# P2.8 — 임시 PIN 잠금

## 기준 입력

- 기준 백로그 schema version: `1.1`
- 기준 백로그 SHA-256: `cf3f4a94d5d2e28ad9dc9bd91e0e506de357f475137a99a3fd9579c2f7e42604`
- 기준 백로그 항목: `P2.8`
- 백로그 개발 상태: `in_review`
- 선행 작업: `P2.6`
- 요구사항 문서: `docs/research.md`
- 구현 기준 패키지 버전: `1.11.0`
- 문서 상태: 구현 및 검사 근거를 반영한 설명 문서 작성 완료. 문서화 완료와 개발 작업 완료는 별도로 관리한다.

## 목적

편집 화면에 진입하기 전에 PIN을 요구하고, 로컬 단계에서 PIN의 SHA-256 해시를 Expo SecureStore에 저장한다. 백로그의 완료 기준은 “PIN 미입력 시 편집 화면 진입 불가, 해시가 secure-store에 저장됨”이다.

## 쉬운 설명

편집 영역은 `PinGate` 뒤에 있다. 처음에는 숫자 4~8자리 PIN을 두 번 입력해 저장하고 편집을 연다. PIN이 이미 저장되어 있으면 입력한 PIN의 해시를 SecureStore의 해시와 비교해 일치할 때만 편집 화면을 연다. PIN 원문은 저장하지 않는다.

## 필요한 입력

- `P2.6`의 `TimetableEditor`와 요일 복사 등 편집 영역.
- 숫자 4~8자리 PIN과 최초 설정 시 확인 PIN.
- Expo 네이티브 모듈 `expo-secure-store`.
- SecureStore 키 `timetable.pin.sha256.v1`.

## 결과물 및 구현

- `expo-secure-store`를 Expo 방식으로 설치하고 의존성에 등록했다.
- `src/security/pin.ts`
  - PIN 입력 형식(숫자 4~8자리) 검증
  - 표준 SHA-256 해시 계산
  - SecureStore에 해시 저장·조회·검증
- `src/components/PinGate.tsx`
  - 최초 PIN 설정 및 확인 입력
  - 기존 PIN 입력과 검증
  - PIN 저장 중에는 입력과 제출을 잠그고, 저장이 끝날 때까지 편집을 열지 않음
  - SecureStore 조회가 끝날 때까지 편집 잠금 유지 및 조회 실패 시 재시도 안내
  - 앱이 active 상태를 벗어나면 편집 잠금으로 되돌리는 AppState 재잠금
  - active 복귀 시 진행 중인 저장이 끝날 때까지 기다린 뒤 SecureStore PIN 상태를 재조회
  - background 전환과 active 복귀 재조회 시 PIN·확인 입력값을 비워, 이전 입력만으로 재잠금 상태를 해제할 수 없도록 처리
  - 비동기 PIN 조회·검증이 진행되는 동안 세션 번호를 확인해, background 전환으로 무효화된 이전 요청이 편집 잠금을 다시 열지 못하도록 차단
  - background 중 PIN 저장이 완료되어도 현재 세션이 유효할 때만 `configured` 상태를 반영하고 편집을 연다. 오래된 저장 결과는 무시한다.
  - PIN 저장소 오류·불일치·잘못된 형식 안내
  - 검증 전 편집 children을 노출하지 않는 편집 잠금
- `app/index.tsx`
  - `TimetableEditor`와 `WeekdayCopy`를 `PinGate` 안에 배치

## 수행 순서

1. `P2.6`의 편집 영역을 `PinGate`로 감싼다.
2. 앱 시작 시 SecureStore에 해시가 있는지 확인하며, 조회가 끝날 때까지 편집 영역을 잠근다.
3. 해시가 없으면 PIN과 확인 PIN을 받아 형식을 검증하고 SHA-256 해시를 저장한다.
4. 해시가 있으면 입력 PIN을 같은 방식으로 해시해 저장값과 비교한다.
5. 최초 저장 또는 검증 성공 때만 편집 children을 표시한다.
6. SecureStore 조회가 실패하면 편집을 잠근 상태로 재시도 동작과 오류 메시지를 안내한다.
7. 앱이 active가 아니게 되면 즉시 `unlocked` 상태를 해제하고 세션 번호를 증가시켜 다시 PIN을 요구한다.
8. active로 복귀하면 SecureStore를 다시 조회해 현재 PIN 설정 상태를 확인한다.
9. 비동기 저장·검증이 끝났을 때 시작 세션과 현재 세션이 다르면 `configured` 상태와 `unlocked` 상태를 적용하지 않는다.
10. background 중 저장 완료 결과가 이전 세션을 통해 편집을 무단으로 열지 못하도록 차단한다.
11. background 전환과 active 복귀 재조회 때 PIN·확인 입력값을 초기화해 재입력을 요구한다.
12. PIN 불일치·형식 오류·SecureStore 오류를 각각 사용자 메시지로 안내한다.
13. PIN 해시 함수와 SecureStore 흐름을 테스트하고 `npm run check` 전체 검사를 실행한다.

## done_when 확인 방법

다음 근거로 백로그의 완료 기준을 대조한다.

- PIN 입력 전에는 `TimetableEditor`와 요일 복사 편집 영역이 표시되지 않는다.
- SecureStore PIN 조회 중에도 편집 영역이 잠겨 있고, 조회 실패 시 재시도 전까지 잠금이 유지된다.
- 최초 PIN 설정 시 숫자 4~8자리와 확인 값 일치를 검사한 뒤 편집을 연다.
- PIN 저장 중에는 입력 변경과 제출을 막고, 저장 완료 전에는 편집을 열지 않는다.
- 저장된 PIN은 원문이 아닌 SHA-256 해시이며, SecureStore 키 `timetable.pin.sha256.v1`에 저장된다.
- 기존 PIN 입력은 저장된 해시와 비교하고, 불일치하면 편집을 열지 않는다.
- 앱이 background/inactive 상태로 전환된 뒤 active로 돌아오면 PIN을 다시 요구한다.
- active 복귀 시 진행 중인 PIN 저장이 끝난 뒤 SecureStore 상태를 다시 조회한다.
- AppState 전환 중 이전 비동기 PIN 요청이 늦게 완료되어도 편집 잠금이 다시 해제되지 않는다.
- active 복귀 시 SecureStore를 재조회해 PIN 설정 상태를 갱신한다.
- background 전환 또는 active 복귀 재조회 뒤 PIN·확인 입력값이 비워져, 사용자가 PIN을 다시 입력하지 않으면 잠금 해제가 되지 않는다.
- background 중 완료된 PIN 저장을 포함해 오래된 비동기 결과가 이전 세션의 `configured` 갱신이나 무단 unlock으로 이어지지 않는다.
- `__tests__/pin.test.ts`가 `1234`의 표준 SHA-256 결과와 원문 비보존 동작을 검증한다.
- 최신 전체 `npm run check`가 통과했다: 지침 동기화, 파일 길이, lint, typecheck, Jest 38개, Android debug build.
- 현재 백로그 개발 상태는 `in_review`이며, 문서화 완료와 개발 작업의 `done` 상태를 혼동하지 않는다.
