# P6.12 — 일시정지 대비 확인

## 기준 입력

- Schema version: `1.1`
- SHA-256: `6953a0065453f0b5dbb5802c8d9129426ca438fbf1a4c2b969e7f523bf03a33c`
- 입력 크기: `446050` bytes
- 기준 시각: `2026-10-07T19:18:12.431Z`
- 기준 상태: `done` (owner: `codex`, updated_at: `2026-10-07T19:18:12.411Z`)

## 작업 목적
서버에 접속할 수 없는 상황에서도 딸 폰에 이미 저장된 일정·할 일 데이터가 유지되고, 로컬 알림과 홈 화면 위젯이 계속 동작하는지 확인한다. 동기화 실패가 로컬 데이터를 교체하거나 알림 예약을 망가뜨리지 않는지도 확인한다.

## 쉬운 설명
쉽게 말해, 인터넷을 끊어 서버를 못 쓰게 해도 폰 안에 저장된 내용으로 위젯과 일반 알림이 움직이는지 보는 작업이다. 전체화면 알람까지 성공한 것으로 간주하지 않는다.

## 필요한 입력
제공된 기준 백로그 P6.12(schema 1.1, SHA-256 `b677bb3b2e9880ff7346b50d9f56100156cc16b9dc03a1a8a03562ff8c6c5a1a`), 선행 P6.6의 완료된 동기화 동작, 딸 폰의 로컬 예약 데이터, 서버 접근 불가 시나리오가 필요하다. 근거 문서는 `docs/device-verification-2026-10-08.md`이며 자동 검증은 동기화 실패의 로컬 보존·롤백 사례다. 공유 Supabase를 실제 중지하지 않고 실기기 네트워크 차단으로 오프라인을 모사했다. 별도로 실제 fetchLocalSnapshot 함수 경로에 503/401 오류 결과를 주입한 회귀 테스트를 수행했다. HTTP 서버를 정지하거나 실제 HTTP 오류 응답을 발생시킨 시험은 아니다.

## 결과물
오프라인 상태의 일반 알림 게시 및 자정 위젯 갱신 관찰 기록, 동기화 오류 시 로컬 데이터 보존 자동 테스트 근거, 임시 데이터 정리 및 네트워크 복구 기록. 전체화면 알람 성공은 결과물에 포함하지 않는다.

## 선행 작업
P6.6(동기화: 서버와 SQLite 간 데이터 흐름 및 알림·위젯 갱신)이 선행 작업이다. 기준 입력에서 P6.6은 `done`이며 P6.12의 deps다.

## 수행 순서
1. P6.6 동기화 경로와 이미 예약된 로컬 알림·위젯 데이터를 준비한다.
2. 공유 서버를 실제로 중지하지 않고 폰의 Wi-Fi·모바일 데이터 연결을 차단해 오프라인을 모사한다.
3. 날짜 변경에 따른 위젯 갱신과 예약된 일반 알림 게시를 관찰하고 시각·알림 식별 정보를 기록한다.
4. 업로드/다운로드 실패 시 로컬 교체·알림 재예약이 생략되는지, 실제 fetchLocalSnapshot 함수 경로에 503·401 오류 결과를 주입했을 때에도 로컬 교체·동기화 마커·알림/위젯 갱신이 생략되는지, 잘못된 스냅샷 적용 실패 시 롤백되는지 자동 테스트 근거를 확인한다.
5. 임시 테스트 행을 ID와 제목으로 대조해 삭제하고 서버 잔여·폰 반영·향후 예약 제거를 확인한 뒤 네트워크를 복구한다.
6. 완료 조건과 관찰 한계를 함께 기록한다. 자동 테스트는 관찰하지 않은 기기 동작의 증거로 대체하지 않는다.

## done_when 확인 방법
서버 접근 불가 상태에서 딸 폰의 로컬 일반 알림이 게시되고 위젯이 날짜 전환 뒤 갱신된 기록을 `docs/device-verification-2026-10-08.md`에서 대조한다. 동기화 실패 경로는 `sync-runner.test.ts`와 `sync-pull.test.ts`의 오프라인·503·401 로컬 보존, 갱신 생략, 롤백 사례로 확인한다. 실제 Supabase 프로젝트를 정지하지 않았으며, 전체화면 알람의 성공이나 장기간 장애 동작은 이 기록으로 주장하지 않는다.

## 확인 질문
현재 입력에는 추가 사용자 결정이 필요한 미해결 조건이 없다. 실제 공유 서버 중지나 전체화면 알람 실기기 검증을 추가하려면 별도 범위 결정이 필요하다.
