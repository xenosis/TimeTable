## 목적

현재 앱의 기본 시간표는 고정된 하나이다. 사용자(아빠)는 학기 중, 방학, 특강 주간 등 여러 일정표를 이름 붙여 관리하고 필요할 때 선택해 적용하고 싶어 한다. 이 작업은 고정 2개 모드("평소", "방학")를 일반화하여, 사용자가 임의로 많은 시간표 세트를 만들고 이름을 붙여 저장·불러올 수 있도록 DB와 저장소 계층을 정리한다. 기존 `regular`, `vacation` 데이터는 "평소", "방학" 이름의 세트로 자동 이전한다.

## 쉬운 설명

지금까지는 "평소"와 "방학" 두 개 시간표만 저장할 수 있었다. 앞으로는 "2학기", "겨울방학", "7/27주 특강" 등 원하는 대로 시간표 이름을 정하고 여러 개 저장할 수 있다. 기존 "평소", "방학" 데이터는 자동으로 그 이름 그대로 옮겨지고, 필요한 세트를 선택해서 쓸 수 있다. 각 세트 안에는 월~금의 일정 목록이 저장되며, 세트를 "적용"하면 앱 전체에서 그 일정을 사용한다.

## 필요한 입력

- 현재 SQLite DB 스키마
  - `timetable_items` 테이블: `timetable_mode` 칼럼 (기존 데이터)
- 기존 "평소"(regular) 및 "방학"(vacation) 데이터 마이그레이션
  - 기존 데이터가 저장된 DB 파일 위치 확인
  - 마이그레이션 스크립트 또는 수동 처리 방법
- 새 세트 저장 구조
  - 세트 ID, 이름, 생성 일시, 적용 여부 등 메타데이터
  - 각 세트 하의 `timetable_items` 관계

## 결과물

- **SQLite 스키마 변경 (DB 마이그레이션)**
  - 새 테이블 `timetable_sets`:
    ```
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    created_at INTEGER NOT NULL (unix timestamp),
    is_active INTEGER DEFAULT 0,
    description TEXT (선택사항)
    ```
  - `timetable_items` 테이블 수정:
    - 기존 `timetable_mode` 칼럼 제거 (또는 유지하되 미사용)
    - 새 `timetable_set_id TEXT` 칼럼 추가 (foreign key → `timetable_sets.id`)
  - 마이그레이션 스크립트 (`src/db/migrations/` 또는 `getDatabase()` 내부):
    - `timetable_sets` 테이블 생성
    - 기존 `regular` 모드 항목 → `timetable_set_id='builtin-regular'` 세트로 이전
    - 기존 `vacation` 모드 항목 → `timetable_set_id='builtin-vacation'` 세트로 이전
    - 기존 데이터가 없으면 기본 세트 2개 자동 생성
    - `timetable_sets` 테이블에 "평소", "방학" 2개 기본 세트 생성

- **Repository 함수** (`src/db/timetableRepository.ts`)
  - `createTimetableSet(name: string, description?: string): TimetableSetDTO`
    - 새 세트 생성 (빈 상태)
  - `duplicateTimetableSet(sourceSetId: string, newName: string): TimetableSetDTO`
    - 기존 세트의 모든 항목을 복제해 새 세트 생성
  - `renameTimetableSet(setId: string, newName: string): void`
    - 세트 이름 변경
  - `deleteTimetableSet(setId: string): void`
    - 세트와 그 안의 모든 항목 삭제
    - 단, 적용 중인 세트는 삭제 불가 (P8.6 관리 UI에서 확인)
  - `getActiveTimetableSet(): TimetableSetDTO`
    - 현재 적용 중인 세트 조회 (is_active = 1)
  - `setActiveTimetableSet(setId: string): void`
    - 주어진 세트를 적용 (is_active = 1로 설정, 기존 활성 세트는 0으로)
  - `listTimetableSets(): TimetableSetDTO[]`
    - 모든 세트 목록 조회 (생성 순서 또는 이름 가나다순)
  - `getTimetableItemsForSet(setId: string): TimetableItemDTO[]`
    - 해당 세트의 모든 항목 조회
  - `getTimetableItemsForWeekday(weekday: Weekday, setId?: string): TimetableItemDTO[]`
    - 해당 세트 + 요일의 항목 조회 (setId 미제공 시 활성 세트 사용)

- **타입 정의** (`src/types/timetable.ts` 또는 `src/db/timetableRepository.ts`)
  ```typescript
  export interface TimetableSetDTO {
    id: string;
    name: string;
    created_at: number;
    is_active: boolean;
    description?: string;
  }
  
  export interface TimetableItemDTO {
    // 기존 필드 유지
    id: string;
    weekday: Weekday;
    title: string;
    color_key: string;
    icon_key: string;
    // ... 나머지
    timetable_set_id: string; // 새로 추가
  }
  ```

- **단위 테스트** (`__tests__/timetableRepository.test.ts`)
  - `createTimetableSet`: 새 세트 생성 및 ID 부여 확인
  - `duplicateTimetableSet`: 세트 복제 시 항목까지 복제 확인
  - `renameTimetableSet`: 이름 변경 확인
  - `deleteTimetableSet`: 세트와 항목 삭제 확인
  - `setActiveTimetableSet`: 활성 세트 전환 확인 (기존 활성 세트가 0으로 변경)
  - `listTimetableSets`: 목록 조회 순서 확인
  - `getTimetableItemsForWeekday`: 특정 세트의 특정 요일 항목 조회 확인
  - 마이그레이션 시뮬레이션: 기존 regular/vacation 데이터가 정확히 이전되는지 확인
  - 엣지 케이스:
    - 적용 중인 세트 삭제 시도 (실패 확인)
    - 존재하지 않는 세트 조회 (null/error 처리)
    - 빈 세트 생성 후 세트 조회 (빈 배열 반환)

- **마이그레이션 통합** (`src/db/index.ts` 또는 `getDatabase()`)
  - 앱 시작 시 DB 초기화 단계에 마이그레이션 로직 포함
  - 기존 데이터가 있으면 일회성 변환 수행
  - 이후 앱 시작 시 마이그레이션 재실행 방지 (메타데이터 버전 관리)

- **적용 중인 세트 상태 관리** (Zustand store에서, P8.6 이후)
  - 현재 적용 중인 세트 ID를 앱 상태에 유지 (추후 P8.6에서 UI 업데이트 반영)

## 수행 순서

1. 현재 `timetable_items` 스키마 확인 및 `timetable_mode` 칼럼 존재 여부 파악
2. `timetable_sets` 테이블 DDL 작성 및 마이그레이션 초안 작성
3. 마이그레이션 스크립트 구현:
   - 기존 `regular` 항목 조회 → `timetable_set_id='builtin-regular'` 업데이트
   - 기존 `vacation` 항목 조회 → `timetable_set_id='builtin-vacation'` 업데이트
   - `timetable_sets` 테이블에 기본 세트 2개 생성
   - 데이터 없을 경우 기본값 설정
4. `timetableRepository.ts`에 위 함수들 구현
5. `__tests__/timetableRepository.test.ts` 작성
   - 각 함수에 대한 단위 테스트
   - 마이그레이션 시뮬레이션 테스트 (기존 데이터가 정확히 이전되는지)
6. `npm run check` 통과 (jest 포함)
7. 실기기에서 기본 테스트 (필요시 P8.6 UI 완료 후)

  - 기존 vacation 데이터가 "방학" 세트(id='builtin-vacation')로 이전됨을 확인
