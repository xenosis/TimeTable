## 설계 이유

### 1. 서버가 새 id를 부여하는 이유
로컬 SQLite id는 앱이 자체 시퀀스로 발급하고, 서버 PostgreSQL id도 서버의 시퀀스로 발급한다. 로컬 id를 그대로 서버에 넣으면 시퀀스를 맞춰야 하는데, 앱 계정에는 그 권한이 없다. 대신 서버 함수 안에서 로컬 id → 서버 id 매핑(`v_sets`, `v_tasks` JSONB)을 유지하고, 참조 관계(시간표 세트↔항목, 할 일↔완료 기록)를 새 id로 짝지어 넣는다.

### 2. 한 트랜잭션으로 실행하는 이유
이전 중 오류가 나면 부분 데이터가 서버에 남지 않도록 보장한다. 시간표 항목은 세트를 가리키고, 완료 기록은 할 일을 가리키므로 중간에 멈추면 참조 무결성이 깨진다. 함수 안에서 모든 insert를 한 트랜잭션으로 수행하고, 하나라도 실패하면 자동 롤백된다.

### 3. 딸 계정으로만 이전하는 이유
아빠 폰도 로컬 SQLite를 가지고 있는데 (관리 화면 때문에), 아빠가 먼저 비어있는 데이터를 올리면 서버에 "이미 이전됨" 플래그가 생겨 딸 폰의 실제 데이터가 올라가지 못한다. 함수는 `security invoker`라 호출 계정의 역할을 확인하고, 클라이언트는 `canImport()` 함수로 딸 역할을 검증한다.

### 4. 중복 올리기를 거부하는 이유
가족에 이미 데이터가 있으면 insert를 시도하지 않고 예외를 던진다. 초기 이전은 한 번만 일어나야 하고, 이후 동기화(P6.6)는 별도 메커니즘을 통해 진행된다. 실수로 두 번 올려도 서버가 데이터를 중복시키지 않는다.

### 5. tt_gem_rights 테이블을 서버에 추가한 이유
로컬 SQLite 스키마 버전 12(P4.13)에는 보석 자격(5일 연속 달성 시 실물 보석 받을 자격)을 저장하는 `gem_rights` 테이블이 있다. 그런데 서버 스키마(P6.2)는 로컬 버전 11을 기준으로 만들어졌기 때문에 이 테이블이 빠져 있었다. P6.5에서 로컬 데이터를 올릴 때 이 데이터도 함께 이전하려면 서버 테이블이 필요하다. 마이그레이션 파일에서 `tt_gem_rights` 테이블(family_id, child_id, earned_date, state, requested_at, given_at)을 만들고 RLS 정책을 적용했다.
