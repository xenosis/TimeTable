# P4.8 — 할 일 알림

## 기준 입력

- 백로그 schema version: `1.1`
- 백로그 SHA-256: `860da466cee4bccfe3f956c51fa2838585e91fcbd2b133dba6c6bd964d0118e0`
- 백로그 크기: `159098` bytes
- 백로그 기준 수정 시각: `2026-09-27T14:19:01.982Z`
- 기준 항목: `P4.8` (`needs_info`)

## 목적

할 일별 알림을 시간표 알림과 함께 롤링 예약하고, 미완료 할 일에 대해 30분 재알림을 생성한다. P4.8은 할 일 데이터 조회와 30분 재알림 계산만 담당하며, 네이티브 교체 경계(`tasks` owner)와 전체 세대 관리는 P3.4의 공통 메커니즘을 사용한다.

P4.8의 책임:
1. SQLite의 할 일 테이블에서 오늘 미완료 항목을 조회한다.
2. 각 할 일의 알림 시각과 방식(notify/alarm)을 읽어 첫 알림과 30분 뒤 재알림을 계산한다.
3. 이 목록을 P3.4의 공통 네이티브 교체 경계에 `tasks` owner로 전달한다.
4. 할 일 추가·수정·삭제·완료 시 별도의 재예약 요청 경로를 제공한다.

P3.4는 시간표의 실제 데이터와 owner 전체의 교체·복구 메커니즘을 담당하므로, P4.8은 tasks owner 실제 할 일 데이터 검증만 수행한다.

## 쉬운 설명

예를 들어 저녁 7시에 "숙제했니?"를 알리고, 아직 체크하지 않았다면 30분 뒤 다시 알려준다. 완료하면 남은 알림을 다시 계산해서 예약 목록에서 빼낸다. 시간표 알림도 같은 방식으로 처리되는데, 할 일과 함께 한 세대의 예약으로 관리되어 중복을 막는다.

## 필요한 입력

- P4.2의 할 일·완료 기록 로컬 DB 구조 (`tasks` 테이블, `task_completions` 테이블)
- P3.3의 7일 롤링 알림 계산 및 알림 방식 분기
- 할 일별 알림 시각(`remind_time`), 알림 방식(`alert_mode`: `none`/`notify`/`alarm`), 반복 요일(`repeat_weekdays`)
- 각 할 일의 현재 날짜별 완료 여부(`task_completions` 테이블)
- 할 일 추가·수정·삭제 또는 완료 체크 뒤 재예약을 요청할 수 있는 기존 연결
- `docs/needs-info-checklist.md`의 P4.8 검증 절차

P4.2와 P3.3은 백로그에서 `done`으로 기록되어 있다.

## 결과물

- SQLite의 할 일 데이터(제목, 알림 시각, 알림 방식, 반복 요일, 완료 여부)에서 오늘 미완료 할 일을 조회하는 경로
- 오늘 미완료 할 일의 첫 알림 및 30분 뒤 재알림 계산 함수 (`buildTaskRollingNotifications`)
- 시간표 롤링 계산 결과와 할 일 알림 결과를 결합하여 `tasks` owner로 네이티브 교체 경계에 전달하는 경로
- 할 일 추가·수정·삭제·완료 후 별도 재예약 요청 경로 (`requestTaskRollingScheduleRefresh`)
- 할 일 데이터의 재저장·변경·완료·삭제 뒤 예약 정확성 검증 기록

## 선행 작업

- `P4.2` — 할 일 관련 SQLite 테이블·마이그레이션: `done`
- `P3.3` — 7일 롤링 알림 목록 계산: `done`
- `P3.4` — 예약 실행: P3.4의 공통 네이티브 교체 경계와 공통 메커니즘(앱 재시작·재부팅·교체 중단 복구)이 먼저 구현되고 실기기 검증이 완료되어야 한다. P3.4가 `tasks` owner 검증까지 책임지기 때문이다.

## 수행 순서

1. P4.2와 P3.3의 완료 기록을 확인한다.
2. 할 일의 알림 시각·방식·반복 요일을 저장하고 완료 상태를 조회하는 DB 경로를 만든다.
3. 오늘 미완료 할 일의 첫 알림과 30분 뒤 재알림을 계산한다 (`buildTaskRollingNotifications`).
4. 시간표 롤링 예약 결과와 할 일 알림 결과를 결합한다.
5. 결합된 목록을 `tasks` owner로 P3.4의 공통 네이티브 교체 경계에 전달한다.
6. 할 일 추가·수정·삭제·완료 시 별도의 재예약 요청 경로를 연결한다 (`requestTaskRollingScheduleRefresh`).
7. 단위 테스트와 통합 검사를 진행한다.
8. P3.4의 공통 교체 경계 실기기 검증(앱 재시작·재부팅·교체 중단) 완료 뒤, `docs/needs-info-checklist.md`의 P4.8 절차대로 딸 폰 실기기에서 할 일 실제 데이터 검증을 수행한다.

## done_when 확인 방법

`docs/needs-info-checklist.md`의 "P4.8 할 일(tasks) owner 실제 예약 확인 (딸 폰 실기기)" 섹션에 기록된 대로, 딸 폰(SM-A245N) 실기기에서 다음을 확인한다:

P3.4의 공통 교체 경계 확인(앱 재시작·재부팅·교체 중단)이 먼저 끝나 있어야 한다. 할 일(tasks) owner는 미완료 상태면 첫 알림 외에 30분 뒤 재알림이 하나 더 정상 생성되므로 기대 건수가 시간표와 다르다: **완료 전 2건(첫 알림 + 30분 재알림), 완료 체크 뒤 0건.**

1. 알림 방식을 지정한 미완료 할 일을 현재 시각보다 3분 뒤로 저장한다. 같은 내용을 즉시 한 번 더 저장한다.
2. 제목을 바꾸고 2분 뒤 시각으로 저장한다. 마지막 내용을 다시 한 번 저장한다.
3. `adb shell dumpsys alarm`에서 tasks owner 예약이 마지막 세대(첫 알림 + 30분 재알림 2건)만 남는지 확인하거나, 실제로 두 알림이 순서대로 도착하는지 확인한다.
4. 같은 할 일을 완료 체크한다. `dumpsys alarm`에서 tasks owner의 해당 할 일 재알림이 취소돼 0건인지 확인한다.
5. 알람 방식으로 설정한 할 일로 P3.4의 8번과 같은 잠금 화면 알람(전체 화면·반복음·끄기)을 확인한다.
6. 아직 오지 않은 할 일을 삭제한다. `dumpsys alarm`에서 tasks owner의 활성 예약이 0건인지 확인한다.

**통과 기준**: tasks owner는 실제 할 일 데이터로 재저장·제목/시각 변경·완료 체크·삭제 각각에서 기대 건수(완료 전 2건, 완료·삭제 후 0건)만 정확히 남고, 딸 폰 잠금 화면 알람이 정상 동작한다.
