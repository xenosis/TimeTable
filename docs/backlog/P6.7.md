## 작업 목적
앱이 켜진 상태에서 서버의 가족 데이터 변경이 Realtime으로 즉시 전달되고, 앱이 백그라운드에서 돌아올 때도 놓친 변경을 동기화한다.

## 쉬운 설명
딸이 앱을 켜 두고 있을 때 아빠가 서버에서 시간표나 할 일을 바꾸면, 딸 폰이 2초 안에 그 변경을 감지하고 화면을 갱신한다. 예를 들어 아빠가 서버에 새 할 일을 추가하면 딸 폰의 앱에서 그 할 일이 나타난다.

## 필요한 입력
1. 서버 데이터베이스에 `20261007000100_tt_realtime.sql` 마이그레이션 적용
2. 앱 측 `subscribeFamilyChanges()` 함수와 `SyncLifecycle` 컴포넌트
3. 앱 시작 또는 로그인 후 첫 동기화는 별도 처리(P6.13~P6.15)

## 결과물
- 서버의 가족 데이터 테이블(시간표 항목, 할 일 등)이 Realtime postgres_changes로 게시되고 필터됨
- 앱이 켜진 동안 서버 변경이 2초 이내에 감지되어 동기화 신호 발생
- 앱이 백그라운드에서 다시 활성화되면 그사이 놓친 변경 확인
- 실기기에서 서버 변경이 약 3초 내 반영됨(2초 모으기 + 동기화)

## 상세 설명

### 1. 서버 Realtime 설정 (마이그레이션 20261007000100_tt_realtime.sql)

#### 게시(publication)에 들어간 테이블 (11개)
```
tt_periods, tt_timetable_sets, tt_timetable_settings, tt_timetable_items, 
tt_day_exceptions, tt_tasks, tt_task_completions, tt_task_completion_history, 
tt_sticker_ledger, tt_rewards, tt_gem_rights
```

**들어간 이유:**
- 모두 가족 데이터이며, 시간표·할 일·완료 기록·보상·보석 등 앱 화면에 표시되는 테이블
- RLS 정책이 `family_id`로 행 범위를 제한하므로 Realtime도 이 가족 구성원에게만 변경이 전달됨

#### 제외된 테이블
- **`tt_devices`**: 매 동기화마다 `last_synced_at`이 바뀌어 무한 루프(동기화가 동기화를 부름) 위험
- **`tt_families`, `tt_family_members`**: 앱 화면 데이터가 아님 (가족 정보 표시 안 함)

#### replica identity full 설정
마이그레이션에서 모든 테이블을 `alter table public.{테이블} replica identity full`로 설정:
- 테이블 크기가 작아서 부담 적음
- 삭제(delete) 이벤트도 모든 열 값을 포함해 `family_id`로 필터링 가능

### 2. 앱 구독 구현 (realtimeSync.ts)

#### subscribeFamilyChanges 함수의 동작
```typescript
export const realtimeTables = [
  'tt_periods', 'tt_timetable_sets', ..., 'tt_gem_rights'
] as const;

export function subscribeFamilyChanges(familyId: string, onChange: () => void, debounceMs = 2000): () => void
```

**특징:**
- 11개 테이블 각각에 대해 `postgres_changes` 이벤트 구독
- 필터: `family_id=eq.{familyId}` — 이 가족의 변경만 받음
- 변경 내용 자체는 쓰지 않고, '무언가 바뀌었다'는 신호로 동기화를 한 번 실행

#### 2초 모으기(debounce)
연달아 오는 변경들을 2초 동안 모았다가 한 번만 동기화 신호 발생:
- 예: 서버에서 3개 행을 동시에 삽입하면 `onChange()` 3번 아니라 1번만 호출
- 이유: 한 번의 동기화로 여러 변경을 함께 반영하려고

#### 재연결 처리 (1.53.2 개선)
```typescript
channel.subscribe((status) => {
  if (status === 'SUBSCRIBED') {
    if (subscribedOnce) schedule();  // 재연결: 놓친 변경 확인
    subscribedOnce = true;
  }
  // 오류·시간 초과는 라이브러리 자동 재참여에 맡김
  // CLOSED만 새 채널로 다시 구독
});
```

**로직 (v1.53.1 vs 1.53.2):**
- v1.53.1: `CHANNEL_ERROR` 때 채널을 지우고 새로 만듦 → 비행기 모드 on/off 뒤 변경이 오지 않음 (2026-10-07 22:48~22:54 실기기 확인)
- v1.53.2: 오류/타임아웃은 라이브러리 자동 재참여에 맡기고, 다시 `SUBSCRIBED`로 돌아오면 한 번 동기화. `CLOSED` 상태만 새 채널로 재구독
- 평상시 반영 시간: v1.53.1에서 약 4초, v1.53.2 실기기 재확인 예정

### 3. 앱 복귀 연결 (SyncLifecycle.tsx)

#### AppState 이벤트
```typescript
AppState.addEventListener('change', (state) => {
  const current = syncTarget(getAccount());
  if (state === 'active' && current) void runSync(current);
});
```

**동작:**
- 앱이 백그라운드에서 활성화되면(`state === 'active'`) 한 번 동기화
- 원인: Realtime이 백그라운드 동안 놓친 변경을 받으려고
- 로컬 모드(비로그인)에서는 실행 안 함

#### Realtime 구독 통합
```typescript
useEffect(() => {
  if (!familyId) return undefined;
  return subscribeFamilyChanges(familyId, () => {
    const current = syncTarget(getAccount());
    if (current?.familyId === familyId) void runSync(current);
  });
}, [familyId]);
```

**특징:**
- familyId가 정해지면 구독 시작 (로그인할 때)
- 변경 신호가 오면 현재 로그인 정보로 동기화 실행
- familyId가 달라지거나 정해지지 않으면 구독 해제

### 4. Jest 테스트 (sync-realtime.test.ts)

4가지 시나리오 검증:

1. **구독 설정**: 11개 테이블 구독, `tt_devices` 미포함, family_id 필터 확인
2. **변경 모으기**: 연달아 온 신호 3개가 2초 모으기로 1번 호출
3. **재연결 처리**: 첫 연결은 신호 안 보냄, 재연결은 1번 신호 발생
4. **구독 해제**: `unsubscribe()` 호출 시 채널 삭제 및 대기 중인 신호 취소

## 주의 사항

1. **이메일, 비밀번호, PIN, 키 값**: 이 문서에 기록하지 않음
2. **삭제 기록 없음**: 삭제한 행의 변경만 알 수 있고 "어떤 행이 삭제됐는지"는 알 수 없음 (다른 이유로 이미 설계된 상태)
3. **백그라운드 제약**: 앱이 완전히 종료되면 Realtime 구독이 끊어짐 (OS 정책)
4. **오프라인 상황**: 인터넷 끊김 시 Realtime 이벤트가 오지 않으므로 앱 복귀 시 동기화로 보충
