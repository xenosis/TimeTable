# P6.18 — 딸 폰 실시간 반영·알림 탭 동기화 누락 조사

## 기준 입력

- Schema version: `1.1`
- SHA-256: `7be6c32d8c2b5cbd904c274ef9731e75887fd6d5a8683716b8f2de346b0816d3`
- 기준 상태: `in_progress` (담당 `codex`, 갱신 `2026-10-10T15:47:09.321Z`)
- 백로그 기준은 제공된 stdin 스냅샷만 사용했다.

## 목적

딸 폰에서 서버 변경이 앱 실행 중 빠르게 보이고, 앱이 꺼져 있을 때 변경 알림을 눌러도 최신 내용이 표시되도록 동기화 경로를 조사·수정한다. 아빠 화면에 표시되는 딸 폰의 마지막 동기화 시각도 실제 동기화 완료와 일치하게 한다.

## 쉬운 설명

아빠가 시간표나 할 일을 바꾸면 딸 폰이 새 내용을 받아 보여야 한다. 딸이 앱을 닫아 둔 상태라도 변경 알림을 누르면 새 내용이 보여야 하고, 아빠 화면의 마지막 동기화 시각도 딸 폰이 실제로 맞춘 때를 가리켜야 한다.

## 필요한 입력

- P6.6 완료 결과와 P6.18의 직접 의존성 상태
- Realtime 구독, 동기화 실행, 알림 탭, 기기 동기화 기록 및 아빠 화면 조회 코드
- 딸 폰(SM-A245N)에서 앱 실행 중/종료 상태를 재현할 수 있는 환경
- 아빠 폰(SM-S918N) 및 서버의 설치본별 `tt_devices` 기록을 대조할 수 있는 환경
- 변경 전후 앱 버전, 회귀 테스트·전체 검사·등록 리뷰 결과

## 결과물

- 실시간 반영, 알림 탭 후 최신 내용, 동기화 시각 불일치의 원인과 수정 내역
- 관련 테스트·전체 검사·등록 리뷰와 확인된 지적의 처리 결과
- 딸 폰과 아빠 폰에서 세 완료 조건을 대조한 버전·관찰 결과·기록

## 선행 작업

- `P6.6`은 기준 입력에서 `done`이며 P6.18의 직접 의존성을 충족한다.
- P6.18은 `in_progress`다. 이전 작업 기록에는 코드 보완, 검사 및 리뷰가 기록되어 있으나, 최근 실기기 지연 조사는 진행 중이다.

## 수행 순서

1. 딸 폰에서 앱을 켠 채 서버 `tt_tasks` 변경을 재현하고 Realtime 구독 준비·이벤트 수신·동기화 호출·화면 반영을 추적한다.
2. 앱을 종료한 뒤 변경 알림을 탭해 계정 복원, 가족 확인, 새 서버 조회와 화면 반영 순서를 확인한다.
3. 설치본과 구형 `tt_devices` 행의 동기화 기록 갱신 경로 및 아빠 화면 조회 대상을 대조한다.
4. 확인된 원인을 수정하고 회귀 테스트, 전체 검사, 등록 리뷰를 수행해 근거 있는 지적을 반영한다.
5. 딸 폰과 아빠 폰에서 세 완료 조건을 확인하고 버전·관찰 시각·서버 기록·화면 결과를 기록한다.

## done_when 확인 방법

- 딸 폰 앱이 켜진 상태에서 서버 변경 후 수 초 안에 최신 내용이 화면에 표시되는지 확인하고 관찰 시각·버전을 남긴다.
- 딸 폰 앱을 종료한 상태에서 변경 알림을 탭했을 때 열린 직후 최신 내용이 보이는지 확인한다.
- 같은 동기화 실행의 실제 완료 시각, 설치본 `tt_devices` 기록, 아빠 화면의 시각을 대조한다.
- 관련 테스트와 전체 검사 통과, 등록 리뷰 및 지적 반영, 두 기기 실기기 근거 기록을 확인한다.

## 현재 확인 기록 (기준 입력 기준)

### 발견 내용

- 1.62.1 딸 폰에서 앱 실행 중 서버 `tt_tasks` 이름을 SQL로 바꿨으나 30초 넘게 화면 반영과 동기화 기록이 없었다. `supabase_realtime` 게시에 `tt_tasks`가 포함된 것은 확인됐지만, 그때 앱이 이벤트를 수신해 `runSync`를 호출했는지는 미확인이다.
- 아빠 폰 저장 후 딸 폰에 변경 알림이 도착하고 탭으로 앱도 열렸지만, 직후 최신 할 일이 보이지 않았다. 당시 두 `tt_devices` 행 중 설치본 행에는 푸시 토큰이 있었지만 `last_synced_at`은 없고, 구형 행에는 토큰 없이 시각만 있었다.

### 기준 입력에 적힌 진행 이력

- 1.62.4/168 단계에서 알림 탭의 캐시 복원 및 새 조회 대기, Realtime 수신 준비 대기, 알림·위젯 갱신 완료 대기와 설치본 기기 기록 경로 보완이 기록됐다. authenticated 역할의 설치본 격리 등 검증, 전체 검사(87 suites/526 tests 및 Android build), push-tests 결과도 기록됐다.
- 1.62.9/173 단계에서 전체 검사(89 suites/533 tests, Android build, push-tests), 실제 authenticated 역할의 롤백 검증, 등록 병렬 리뷰 완료가 기록됐다. 이후 운영 `tt_record_device_sync` 적용 승인과 적용 결과도 로그에 있다.
- 2026-10-10 15:41 UTC 로그에는 두 폰 1.62.9/173 설치, 설치본 행의 서버 시각 및 딸 푸시 토큰 확인이 기록됐다. 원격 지급은 서버에서 성공했으나 딸 화면의 대기 문구가 남아 재현됐고, 임시 요청 데이터는 정리됐다고 기록됐다. 1.62.10/174 단계 진단 변경의 전체 검사·리뷰 및 커밋·푸시도 기록됐다. 잠금 화면 때문에 단계 관찰은 이후로 미뤄졌다고 적혀 있다.
- 최신 로그(15:47:09 UTC)는 잠금 해제 후 딸 폰의 1.62.10 진단 로그에서 서버 조회, 로컬 반영, 기기 갱신, 서버 시각 기록 단계가 완료된 실행을 관찰했다고 기록한다. 정확히 어느 단계에서 지연되는지와 소요 시간을 실제 변경으로 추가 확인 중이다.
- 별도 `tt-push-worker` 배포는 `verify_jwt=false` 설정에 대한 자동 승인 검토가 거절해 사용자 판단을 요청한 상태라고 기록돼 있다. 이것은 P6.18의 세 완료 조건 자체가 완료됐다는 근거는 아니다.

### 코드 판독 (실기기 성공 증거와 구분)

- `src/sync/realtimeSync.ts`는 `tt_tasks`를 포함한 가족 테이블을 구독하고, 변경 신호를 모아 동기화 콜백을 부르는 구조다. 실제 폰의 이벤트 수신·반영 성공은 별도 실기기 기록으로 확인해야 한다.
- `app/push-change.tsx`는 계정 확인/복원이 끝난 뒤 자녀 계정 및 가족을 확인하고 알림 탭 동기화를 요청하는 구조다. 기준 입력의 과거 재현은 최신 빌드에서 이 경로가 성공했음을 입증하지 않는다.
- `src/sync/syncRunner.ts`는 서버 내용을 로컬에 반영하고 알림·위젯 갱신을 기다린 뒤 기기 동기화 기록을 요청한다. `src/server/childDeviceStatus.ts`는 설치 ID와 동기화 시각이 있는 자녀 기기 중 가장 최근 시각을 아빠 화면 자료로 선택한다.
- 위 코드는 경로의 존재를 확인한 것이며, 지연의 정확한 원인, 운영 환경에서의 최신 내용 표시, 실제 시각 일치 여부를 증명하지 않는다.

## 완료 조건 대조

| 완료 조건 | 기준 입력에서 확인된 근거 | 판정 |
|---|---|---|
| 앱 실행 중 서버 변경이 수 초 안에 반영 | 이전 1.62.1의 30초 초과 미반영 재현. 1.62.10 단계 로그의 동기화 완료 관찰은 있으나 수 초 내 반영을 확인한 기록은 없음 | 미확인 |
| 앱 종료 상태에서 알림 탭 직후 최신 내용 표시 | 과거 재현에서 최신 내용 미표시. 최신 앱에서 성공한 실기기 기록 없음 | 미확인 |
| 아빠 화면의 딸 폰 마지막 동기화 시각이 실제와 일치 | 설치본 기록 RPC 적용 및 실행 단계 로그는 있으나 같은 실행에서 서버 기록과 아빠 화면을 대조한 결과 없음 | 미확인 |
| 테스트·전체 검사·리뷰·두 기기 실기기 근거 기록 | 검사·리뷰 이력과 일부 두 기기 설치 기록은 있음. 위 세 동작의 최신 성공을 입증하는 두 기기 근거는 없음 | 일부 확인, 완료 조건 미충족 |

따라서 이 기준 입력만으로 P6.18을 `done`으로 판단할 수 없다. 진행 중인 지연 재현 결과와 세 완료 조건의 최신 두 기기 확인을 기록한 뒤 다시 대조해야 한다.

## 확인 질문

- 최신 앱에서 앱 실행 중 서버 변경이 실제로 몇 초 만에 화면에 반영되는가? 정확한 변경 시각, 화면 반영 시각, 버전은 무엇인가?
- 앱 종료 상태에서 알림을 눌렀을 때 최신 내용이 열린 직후 보이는가? 성공/실패 결과와 관찰 기록은 어디에 남길 것인가?
- 같은 실행의 서버 설치본 동기화 시각과 아빠 화면 표시가 일치하는가?
- 로그에 언급된 `verify_jwt=false` 푸시 작업자 배포 승인은 별도 사용자 결정 사항이다. 해당 배포를 진행할지에 대한 답이 있는가?
- 리뷰에 남은 자기 기기 직접 쓰기 RLS 범위와 “수 초”의 구체적 허용 시간은 이 기준 입력만으로 결정되지 않는다. 완료 기준에 추가 해석이 필요한가?

이 문서는 schema version `1.1`, SHA-256 `7be6c32d8c2b5cbd904c274ef9731e75887fd6d5a8683716b8f2de346b0816d3`인 stdin 스냅샷을 기준으로 작성했다. 기준 입력 뒤의 결과를 추정해 포함하지 않았다.
