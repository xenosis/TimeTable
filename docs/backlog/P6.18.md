# P6.18 — 딸 폰 실시간 반영·알림 탭 동기화 누락 조사

## 기준 입력

- Schema version: `1.1`
- SHA-256: `4d9faf2e4e870d0d37817335094b290371153dfe995274af78727fdd249b19c0`
- 기준 상태: `needs_info` (담당 `codex`, 기준 시각 `2026-10-10T09:47:50.152Z`)
- 이 문서는 제공된 stdin 스냅샷만 백로그 기준으로 사용한다.

## 목적

딸 폰에서 서버 변경이 빠르게 보이도록 하고, 앱이 꺼져 있을 때 변경 알림을 눌러도 최신 내용으로 열리게 한다. 아빠 화면의 딸 폰 마지막 동기화 시각도 실제 기기 동기화와 일치시킨다.

## 쉬운 설명

아빠가 시간표나 할 일을 바꿨을 때 딸 폰이 바로 알아채고, 알림을 눌렀을 때도 새 내용이 보이도록 고친다. 아빠 화면에는 딸 폰이 실제로 서버와 맞춘 시각을 표시한다.

## 필요한 입력

- P6.6 완료 결과와 현재 동기화·Realtime·알림 탭 코드
- 재현 대상 딸 폰 SM-A245N 및 앱 실행 중/종료 상태에서 확인할 수 있는 환경
- 아빠 폰과 `tt_devices` 서버 기록을 대조할 수 있는 환경
- 기준 시점 앱 버전 1.62.1 재현 정보 및 이후 수정·검증 기록

## 결과물

- 세 증상(앱 실행 중 실시간 반영, 종료 상태 알림 탭 후 최신 내용, 아빠 화면 동기화 시각)의 원인과 수정
- 회귀 테스트, 전체 검사, 등록 리뷰 결과와 지적 반영 내역
- 두 기기에서 완료 조건을 확인한 앱 버전·관찰 결과 기록

## 선행 작업

- `P6.6` 서버 동기화: 기준 입력에서 `done`; P6.18의 직접 의존성 충족
- P6.18 착수 로그: 1.62.1 인계 상태, 알림 탭의 계정 확인 대기, Realtime 재연결, 설치본 동기화 기록을 조사하고 회귀 검증·실기기 확인 예정
- 완료 판단에는 두 기기의 실제 확인이 필요하며, 기준 입력의 최신 기록에서는 미완료다.

## 수행 순서

1. 앱 실행 중인 딸 폰에서 서버 `tt_tasks` 변경을 재현하고 Realtime 구독 준비, 이벤트 수신, 동기화 실행, 화면 표시까지 확인한다.
2. 앱이 종료된 상태에서 변경 알림을 탭해 계정 복원, 가족 확인, 새 서버 조회와 화면 반영 순서를 확인한다.
3. 설치본 및 구형 `tt_devices` 행 중 어느 행이 동기화 때 갱신되는지, 아빠 화면이 어떤 기록을 표시하는지 대조한다.
4. 원인을 수정하고 관련 회귀 테스트, 전체 검사, 등록된 리뷰를 수행해 확인된 지적을 반영한다.
5. 딸 폰과 아빠 폰에서 세 완료 조건을 확인하고 앱 버전·관찰 시각·서버 기록·화면 결과를 남긴다.

## done_when 확인 방법

- 앱을 켜 둔 딸 폰에서 서버 변경 후 수 초 내 최신 내용이 보이는지 확인한다.
- 앱을 종료한 뒤 변경 알림을 눌렀을 때 앱이 열리자마자 최신 내용이 보이는지 확인한다.
- 동기화 성공 시각을 서버의 딸 설치본 기록 및 아빠 화면 표시와 대조한다.
- 관련 테스트와 전체 검사 통과, 등록 리뷰 및 반영, 두 기기 실기기 근거를 모두 확인한다.

## 현재 확인 기록 (기준 입력 기준)

### 발견 내용

- 딸 폰(SM-A245N 1.62.1)에서 앱을 켠 채 서버 `tt_tasks` 이름을 SQL로 변경했으나 30초가 지나도 화면 반영 및 동기화 기록이 없었다. Realtime 게시에 `tt_tasks`가 포함됨은 확인됐고, 앱의 수신 및 `runSync` 호출 여부가 조사 대상이었다.
- 아빠 폰 저장 후 딸 폰에 변경 알림은 도착했고 앱도 열렸지만, 직후 할 일이 표시되지 않았다. 구형 기기의 서버 `last_synced_at`은 앱 재실행 시각까지 갱신되지 않은 것으로 기록됐다.
- 딸 폰의 `tt_devices`에 설치본 행(토큰 있음, `last_synced_at` 없음)과 구형 행(토큰 없음, 시각 있음)이 각각 있었다. 어느 행을 갱신·표시하는지 확인 대상이다.

### 구현·검증 기록

- 최신 로그는 1.62.4/168 보완 검토 단계라고 기록한다. 알림 탭에서 임시 캐시 복원 및 요청 이후 새 조회를 기다리고, Realtime DB 수신 준비 대기 옵션을 적용했다. 알림·위젯 갱신을 기다리고 부분 실패와 기기 기록 인증/RPC 오류를 안내하며, 서버 완료 시각을 성공으로 오인하지 않도록 했다고 기록한다.
- 설치본 증명 RPC의 등록 전후 순서, 설치본 격리, 다른 가족 거절, 계정 전환 토큰 제거를 실제 authenticated 역할로 BEGIN/ROLLBACK 검증 PASS로 기록한다: `.tmp/p618-device-sync-auth-rollback.log`.
- 전체 검사 PASS: 87 suites/526 tests, Android build 및 push-tests. 로그 위치는 `.tmp/p618-quality-1624-records.log`.
- 딸 폰에는 1.62.3/167 설치가 확인됐고 최신 APK 재빌드 예정이라고 기록한다. 운영 RPC는 미적용, 패턴 잠금 및 아빠 폰 미연결로 두 기기 완료 조건은 미검증이다. 등록 재리뷰 뒤 운영 적용 승인과 실제 반영을 확인할 예정이라고 기록한다.

### 코드 판독 (실기기 동작 증거는 아님)

- `src/sync/realtimeSync.ts`에는 `tt_tasks` 구독이 있고, 이벤트 뒤 동기화를 요청하는 경로와 구독 수신 준비 대기 옵션이 있다. 이것은 코드 구조 확인이며 실제 기기에서 이벤트를 받았다는 증거는 아니다.
- `app/push-change.tsx`는 계정 확인/복원이 진행 중이면 기다린 뒤 자녀 계정과 가족을 확인하고 `syncTappedFamilyPush`를 호출한다. `src/push/pushTap.ts`는 현재 자녀 계정의 가족 ID가 알림의 가족 ID와 일치할 때 `runSync(..., { fresh: true })`를 요청한다.
- `src/sync/syncRunner.ts`는 데이터 적용 후 알림·위젯 갱신을 기다리고 설치본 식별 정보를 사용해 `tt_record_device_sync` RPC를 요청한다. `src/server/childDeviceStatus.ts`는 자녀 계정 기기 중 `installation_id`와 `last_synced_at`이 있는 행을 최신순으로 조회해 아빠 화면 표시 자료로 선택한다.
- 위 소스 판독은 현재 코드 경로만 확인한다. 운영 DB RPC 적용, 이벤트 수신·동기화의 실기기 성공, 아빠 화면의 실제 시각 정확성을 입증하지 않는다.

## 확인 질문

- 설치본 기록 RPC의 운영 적용 및 적용 완료 여부를 확인할 구체적인 기록이 기준 입력에 없다. 기준 입력은 운영 반영 완료를 입증하지 않는다.
- 구형 기기 행을 삭제하거나 병합할지는 요구사항에 정해져 있지 않다. 실제 시각 표시가 조회 수정만으로 해결되지 않을 때 데이터 정리 여부를 결정해야 한다.
- 최신 APK로 딸 폰과 아빠 폰에서 세 동작을 확인한 결과가 기준 입력에 없다. 운영 반영 여부를 확인하고 두 기기의 실기기 결과를 기록해야 한다.
