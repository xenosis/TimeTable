# P6.3 — RLS 정책

**기준:** schema 1.1 · SHA-256 `c7c52a033b17d72bfe6c12146a54ec940ffc1c944a48b4224e421df1e33bde76`  
**상태:** in_review  
**담당:** claude

---

## 목적

Supabase 데이터베이스의 행 수준 보안(Row Level Security, RLS) 정책을 설정하여 아빠 계정(parent)과 딸 기기 계정(child)이 각자 권한에 맞게 데이터를 읽고 쓸 수 있도록 합니다. 딸 폰의 PIN은 로컬 화면 잠금일 뿐이므로 서버에서 권한을 확인하지 않습니다.

---

## 쉬운 설명

Supabase는 로그인한 사용자가 누구인지에 따라 같은 테이블을 쿼리할 때 보이는 행(데이터)을 달리할 수 있습니다(RLS). 우리는:
- **아빠 계정**: 가족 데이터를 모두 읽고 쓸 수 있음
- **딸 기기 계정**: 가족 데이터를 읽을 수 있고, 오늘을 포함한 모든 일자의 할 일 완료를 체크할 수 있음
- **로그인 안 함**: 아무것도 접근 불가

이를 정책으로 정의하고, 소속 확인·가족 생성 함수를 만듭니다.

## 미해결 질문 및 확인 필요

- **마이그레이션 이력 테이블**: Doro 공유 프로젝트에는 마이그레이션 이력 테이블이 없음. 이후 변경(P6.7 등)도 같은 방식(`db query -f`)으로 실행할지, 이력 테이블 추가(`migration repair`)를 할지는 사용자 판단 필요.
- **동시 호출 테스트**: tt_create_family의 동시 호출 시나리오는 59건 검증에 포함되지 않음(SQL 수동 실행으로 테스트 불가). 실제 앱에서의 동시 호출 상황은 P6.6 동기화 구현 시 확인 필요.
- **Realtime 게시**: P6.7에서 필요한 테이블만 추가할 예정. 현재는 publication 등록 없음.

## 적용 이후 운영 주의사항 (supabase/README.md 기록)

- **마지막 parent 삭제/강등 금지**: 구성원을 다시 만들어야 하면 계정 복구 불가. 운영할 때 주의.
- **보석 원장이 있는 구성원 삭제**: 계정을 다시 만들려면 원장의 `child_id`를 새 계정으로 옮긴 뒤 지울 것.
- **삭제 전파 없음**: 완료 취소 시 행 삭제이므로, 증분 동기화(P6.6)에서는 삭제 기록(tombstone) 또는 전체 스냅샷 비교 방식을 정해야 함.
