## 작업 목적

Supabase 데이터베이스의 행 수준 보안(Row Level Security, RLS) 정책을 설정하여 아빠 계정(parent)과 딸 기기 계정(child)이 각자 권한에 맞게 데이터를 읽고 쓸 수 있도록 합니다. 딸 폰의 PIN은 로컬 화면 잠금일 뿐이므로 서버에서 권한을 확인하지 않습니다.

---

## 쉬운 설명

Supabase는 로그인한 사용자가 누구인지에 따라 같은 테이블을 쿼리할 때 보이는 행(데이터)을 달리할 수 있습니다(RLS). 우리는:
- **아빠 계정**: 가족 데이터를 모두 읽고 쓸 수 있음
- **딸 기기 계정**: 가족 데이터를 읽을 수 있고, 오늘 할 일 완료만 체크할 수 있음
- **로그인 안 함**: 아무것도 접근 불가

이를 정책으로 정의하고, 소속 확인·가족 생성 함수를 만듭니다.

- **검증 내용**:
  1. 아빠 계정으로 로그인 후 `select * from public.tt_families`로 자신의 가족 데이터만 보임
  2. 딸 기기 계정으로 로그인 후 시간표·할 일 읽음, 완료 체크 가능, 가족 정보 수정 불가
  3. 비로그인 상태에서 모든 쿼리 거부
  4. 크로스 패밀리(다른 가족의 데이터) 접근 불가
- **다음 단계**: P6.5(데이터 이전) 또는 완성 후 실제 프로젝트에서 진행 예정

### 딸 계정 쓰기 범위 (사용자 확인 필요)
- **구현**: 같은 가족 구성원(아빠·딸)은 시간표·교시·휴일·할 일·완료 기록·보석 원장·보상 목표를 모두 읽고 쓸 수 있다. 날짜 제한(오늘 것만)은 두지 않았다. 오프라인에서 체크한 기록이 나중에 올라오기 때문이다.
- **근거**: D7(2026-10-01) 딸 폰 PIN은 로컬 화면 잠금이라 딸 계정에 시간표·할 일 수정 권한을 준다. 완료 체크와 보석 적립·보상 사용은 앱이 직접 기록해야 해서 원장·보상도 쓰기가 필요하다.
- **사용자에게 확인할 것**: 딸 계정에 보상 목표·보석 원장·교시·휴일 쓰기와 과거 날짜 체크까지 허용해도 되는지(허용하지 않으려면 서버에서 따로 기록하는 함수가 필요하다).

### 다음 구성원 추가 시나리오

## 보안 고려 사항

1. **소속 확인 함수의 정보 유출 방지**
   - `security definer`로 호출자 권한과 무관하게 자신의 소속만 조회
   - 다른 사용자의 가족 정보 열람 불가

2. **인증되지 않은 사용자 차단**
   - 모든 테이블에서 `anon` 권한 회수
   - 로그인한 사용자(authenticated 역할)만 접근

3. **가족 데이터 격리**
   - 모든 정책에서 `family_id` 확인 필수
   - 크로스 패밀리 접근 불가

4. **parent 역할 제한**
   - 가족 정보 수정, 구성원 추가·삭제는 parent만 가능
   - child 역할로는 읽기만 허용

5. **auth.uid() 성능**
   - 정책 내에서 `auth.uid()` 중복 계산 방지
   - `(select auth.uid())`로 한 번만 평가
