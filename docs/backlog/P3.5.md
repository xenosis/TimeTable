# P3.5 — 재예약 시점 연결

## 기준 입력

- 백로그 schema version: `1.1`
- 백로그 SHA-256: `61568fc7225e3df4e0b71db6293ab317e7874f64874dee78360c9f89f588cef7`
- 기준 입력 경로: `backlog.json`의 `P3.5` 항목(stdin 제공본)
- 기준 항목: `P3.5`
- 상태: `in_progress`
- 상위 단계: `P3`
- 선행 작업: `P3.4`
- 기준 입력 바이트: `133616`
- 기준 입력 modifiedAt: `2026-09-25T00:57:09.343Z`

## 목적

시간표 알림 예약이 필요한 시점을 앱의 네 가지 경로에 연결한다.

1. 앱 실행
2. 시간표 데이터 변경
3. 앱 복귀
4. 백그라운드 주기 작업(`expo-background-task`)

## 쉬운 설명

시간표가 바뀌거나 앱을 다시 열었을 때, 이미 등록된 알림을 정리하고 최신 시간표 기준으로 다시 예약한다. 앱을 한동안 사용하지 않아도 백그라운드 작업이 같은 재예약을 수행하도록 연결하는 작업이다.

## 필요한 입력

- P3.5의 기준 요구사항: “4가지 트리거 각각에서 재예약이 호출됨”
- 선행 예약 기능 P3.4의 재예약 경계
- 시간표 데이터 변경 이벤트
- 앱 실행 및 앱 복귀 이벤트
- Expo SDK 57과 호환되는 `expo-background-task`, `expo-task-manager` 구성
- 알림 예약 계산·채널·네이티브 예약 경로의 기존 구현

입력이나 세부 정책이 백로그에 명시되지 않은 경우 임의로 정하지 않고 확인 질문으로 남긴다.

## 결과물

- 네 가지 트리거에서 공통 재예약 경계를 호출하는 연결
- 백그라운드 주기 작업 등록 및 재예약 호출 연결
- 각 트리거가 호출되었음을 확인할 수 있는 테스트 또는 구현 확인 기록
- `done_when` 대조 결과와 미확인 항목 기록

코드·JSON 변경은 이 문서의 범위에 포함하지 않는다. 백로그에 정의되지 않은 동작 정책은 확인 질문으로 남긴다.

## 선행 작업

- `P3.4` — 예약 실행: 기존 예약 전체 취소 후 다시 예약하는 경계
- P3.4는 현재 기준 입력에서 `in_review`이며, P3.5는 그 구현 경계를 전제로 진행 중이다. P3.4의 검토가 완료되었다고 추정하지 않는다.

## 수행 순서

1. P3.4의 재예약 호출 경계를 확인한다. P3.4가 `in_review`인 동안에는 해당 구현 경계를 기준으로만 연결한다.
2. 앱 실행 시 재예약을 연결한다.
3. 시간표 데이터 변경 시 재예약을 연결한다.
4. 앱 복귀 시 재예약을 연결한다.
5. `expo-background-task` 및 `expo-task-manager`를 사용해 백그라운드 주기 작업에서 재예약을 호출하도록 연결한다.
6. 네 가지 트리거 각각의 호출 근거를 테스트 또는 구현 확인 기록으로 남긴다.
7. 네 가지 조건이 모두 확인되었을 때만 `done_when` 충족 여부를 기록하고, 그렇지 않으면 미확인 항목을 남긴다.

## done_when 확인 방법

`P3.5`의 조건인 “4가지 트리거 각각에서 재예약이 호출됨”을 다음처럼 대조한다.

| 트리거 | 확인할 내용 | 현재 확인 기록 |
|---|---|---|
| 앱 실행 | 앱 시작 경로에서 재예약 호출 | 구현·검사 완료로 기록됨 |
| 데이터 변경 | 시간표 데이터 변경 뒤 재예약 호출 | 구현·검사 완료로 기록됨 |
| 앱 복귀 | AppState 복귀 경로에서 재예약 호출 | 구현·검사 완료로 기록됨 |
| 백그라운드 주기 작업 | background task가 재예약 호출 | 모듈 설치 후 구현 재개 기록만 있음; 호출 확인 전 |

현재는 네 번째 경로의 호출 확인 기록이 없어 `done_when` 충족으로 확정할 수 없다. 백그라운드 경로 구현과 해당 호출 확인이 끝난 뒤 네 행 모두의 근거를 갱신한다.
