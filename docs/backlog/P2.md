# P2 — 2단계: 시간표 (로컬)

## 기준 입력

- 백로그 schema version: `1.1`
- 백로그 SHA-256: `03e32af2297cb4f061535453f026900b4b908b798e56bde351f9072f7ce29e3d`
- 기준 항목: `P2`
- 기준 상태: `in_review`
- 선행 작업: `P1`
- 문서: `docs/research.md`
- 이 문서는 위 기준 입력만으로 갱신한다. 원본 `backlog.json`과 프로그램 코드는 수정하지 않는다.

## 목적

딸 폰에서 학교·학원·생활 일정을 포함한 시간표를 로컬 SQLite 기준으로 보고, 교시 시간과 요일별 항목을 관리할 수 있게 하는 2단계 작업이다. 색상과 아이콘은 실제 색상값이 아니라 테마 독립적인 의미 키로 저장한다.

## 쉬운 설명

아이가 오늘 시간표와 주간 시간표를 보고, 아빠가 PIN을 입력한 뒤 교시 시간과 시간표 항목을 추가·수정·삭제할 수 있게 한다. 월요일 시간표를 다른 요일로 복사할 수도 있다. 데이터는 현재 서버가 아니라 딸 폰 안에 저장된다.

## 필요한 입력

- P2의 완료 조건: `딸 폰에서 시간표를 보고 수정할 수 있음 (로컬)`
- P2.1의 범위 결정: 학교·학원·생활 일정 포함
- P2.2의 로컬 DB 스키마 및 마이그레이션
- P1.9의 테마 계약·레지스트리·의미 키 해석
- P2.3~P2.9의 구현·검증 기록
- 사용자 실기기 확인: 시간표 추가·수정·삭제 및 달력 입력
- 관련 요구사항: `docs/research.md`, `docs/tasks.md`, `CLAUDE.md`, `AGENTS.md`

## 결과물

- `periods`, `timetable_items`, `day_exceptions`를 포함한 로컬 SQLite 기반
- 교시별 시작·종료 시각 설정
- 오늘 화면과 요일×교시 주간 화면
- 복수 요일·교시/직접 시간·카테고리·테마 의미 키·알림 설정을 포함한 항목 CRUD
- 요일 복사
- PIN으로 보호되는 편집·설정 영역
- 현재 교시·다음 일정 계산 테스트
- 사용자 실기기에서 시간표 CRUD와 달력 입력이 확인된 기록

## 선행 작업

P2는 `P1`에 의존한다. 기준 입력에서 P2의 모든 하위 작업(`P2.1`~`P2.9`)은 `done`으로 기록되어 있으며, P2.1의 범위 결정과 P1.9의 테마 계약도 완료되어 있다. 따라서 현재 남은 일은 새 기능 구현이 아니라 P2 단계 전체의 완료 근거와 독립 검토 결과를 대조하는 것이다.

## 수행 순서

1. 기준 백로그의 schema version과 SHA-256을 고정한다.
2. `docs/research.md`와 `docs/tasks.md`에서 시간표 범위·로컬 DB·아이용 화면·PIN·테마 의미 키 요구사항을 확인한다.
3. P2.1에서 시간표 범위 결정을 기록한다.
4. P2.2에서 SQLite 마이그레이션과 `color_key`·`icon_key` 보존을 확인한다.
5. P2.3에서 교시 시간을 저장·조회하고, P2.4·P2.5에서 오늘·주간 화면을 확인한다.
6. P2.6에서 항목 추가·수정·삭제를 확인하고 P2.7에서 요일 복사를 확인한다.
7. P2.8에서 PIN 보호를 확인하고 P2.9에서 현재·다음 일정 계산 테스트를 확인한다.
8. 사용자 실기기에서 시간표 추가·수정·삭제와 달력 입력을 확인한다.
9. 하위 작업, 선행 작업, 품질 검사, 독립 검토 결과를 P2의 완료 조건과 대조한다.
10. 완료 조건을 충족한 경우에만 메인 에이전트가 백로그 상태를 갱신한다. 이 문서 갱신 작업에서는 상태 변경을 수행하지 않는다.

## done_when 확인 방법

P2의 조건은 `딸 폰에서 시간표를 보고 수정할 수 있음 (로컬)`이다. 다음 근거를 함께 확인한다.

- 보기: 오늘 화면과 주간 화면이 로컬 DB에서 일정과 교시를 읽고 표시하는지 확인한다.
- 수정: PIN 뒤에서 교시 시간과 시간표 항목을 추가·수정·삭제할 수 있는지 확인한다.
- 로컬성: SQLite 마이그레이션과 저장소가 동작하고, 항목의 테마 의미 키가 보존되는지 확인한다.
- 기능 범위: 복수 요일, 요일 복사, 교시/직접 시간, 카테고리와 알림 설정이 하위 작업 근거와 일치하는지 확인한다.
- 실기기: 사용자 확인 기록에서 시간표 추가·수정·삭제와 달력 입력이 모두 확인되는지 대조한다.
- 품질·검토: P2 하위 작업의 검사·검토 근거와 P2의 독립 검토 결과가 존재하는지 확인한다.

## 현재 확인 기록

- P2.1~P2.9: 모두 `done`으로 기록됨.
- P2.1: D5가 확정되어 학교·학원·생활 일정을 모두 시간표 범위에 포함한다.
- P2.2: SQLite v1 마이그레이션, 세 테이블, 키 보존과 테스트 근거가 기록됨.
- P2.3~P2.7: 교시 설정, 오늘·주간 화면, CRUD, 요일 복사와 관련 테스트·검토 근거가 기록됨.
- P2.8: SecureStore 기반 PIN 해시, 편집 영역 보호, 자동 재잠금과 검토 근거가 기록됨.
- P2.9: 현재·다음 일정, 경계 시간, 공백, 역순 입력 정렬 테스트와 검토 근거가 기록됨.
- 사용자 실기기: 시간표 추가·수정·삭제 및 달력 입력을 확인했다는 P2 로그가 있음.
- P2 현재 상태: `in_review`; `2026-09-26T16:31:41.972Z`에 하위 작업·실기기 확인을 대조하고 독립 검토를 요청한 상태다.
- 선행 작업 P1: 기준 입력에서는 `in_progress`이며, P2의 직접 선행 조건으로 기록되어 있다. P2 하위 작업은 모두 `done`이지만 P1 전체 완료 여부는 이 문서에서 새로 판정하지 않는다.
- 품질·독립 검토: 각 하위 작업 로그에 품질 검사와 검토 근거가 기록되어 있으나, P2 부모에 대한 이번 독립 검토의 최종 결과는 아직 기준 입력에 없다.
- 이 문서 자체는 P2의 완료를 선언하지 않으며, 독립 검토 후 메인 에이전트가 최종 상태를 판단한다.

## 확인 질문

- 백로그의 P2 완료 조건에는 실기기에서 어떤 화면·동작을 어느 정도까지 확인해야 하는지 추가 기준이 없다. 현재 기록된 사용자 확인(추가·수정·삭제·달력 입력) 외에 별도 실기기 시나리오가 필요한가?
- P2 완료 후 P3 알림 예약과의 경계를 어디까지 P2 실기기 회귀 범위에 포함할지는 백로그에 명시되지 않았다. 별도 범위를 정할 필요가 있으면 사용자 결정이 필요하다.
