# P6.6 — 동기화: 서버 → SQLite → 알림 재예약 → 위젯 갱신

## 기준
- 백로그 schema: 1.1
- 백로그 sha256: 86894def7f03d9e5155fca3e3ecfbd1a32bb7f6fda8dc9cb25145da30a139496
- 백로그 bytes: 51194
- 개발 상태: todo
- 문서화 상태: 작성됨

## 작업 목적
오프라인 캐시와 완료 체크 대기열을 포함한 동기화를 구현한다.

## 쉬운 설명
쉽게 말해, 동기화: 서버 → SQLite → 알림 재예약 → 위젯 갱신을 백로그 범위에서 수행한다.

## 필요한 입력
기준 백로그 P6.6와 관련 요구사항 문서. 백로그에 없는 값은 임의로 정하지 않는다.

## 결과물
온/오프라인 전환 시 데이터 정합성이 유지됨

## 선행 작업
백로그에 기록된 상위 작업과 deps의 완료 결과를 확인한다.

## 수행 순서
1. 범위와 입력을 확인한다.
2. 선행 작업 결과를 준비한다.
3. 백로그 범위만 수행하고 결과를 기록한다.
4. done_when을 확인한다.
5. 개발 완료와 문서화 완료를 구분해 기록한다.

## done_when 확인 방법
온/오프라인 전환 시 데이터 정합성이 유지됨를 결과와 대조하고 확인 근거를 남긴다.

## 하위 작업 분할과 수행 순서

P6.6은 세 개의 하위 작업으로 나뉜다:

1. **P6.13 (받아오기)**: 서버 → 로컬 SQLite 단방향 동기화
   - 로그인 후 앱 시작 시 자동 실행
   - 첫 동기화는 서버 기준으로 로컬 데이터 초기화(P6.5 리뷰 결정: 서버가 신뢰 가능한 원본, 로컬은 캐시)
   - 위젯 체크, 알림 재예약, 위젯 갱신까지 포함

2. **P6.14 (체크·보석 기록 올리기)**: 로컬 변경 → 서버 양방향 동기화
   - P6.13 이후 아이가 한 체크, 완료 기록, 보석 기록을 서버로 올림
   - P6.13의 첫 동기화가 완료된 뒤에 실행 가능

3. **P6.15 (로그인 상태 편집은 서버 먼저 저장)**: 로그인 상태 특수 처리
   - 로그인/로그아웃 변경 시 서버에 먼저 저장한 뒤 로컬 적용
   - P6.13, P6.14 이후 사용자 행동 플로우 안에서 처리

**분할 이유**: 단방향(받아오기)에서 양방향(올리기)으로 진행되며, 매 단계마다 검증과 테스트가 필요하므로 별개 작업으로 관리한다.

## 확인 질문
