**기준 정보**

- 상태: 구현 및 실기기 검증 완료

---

## 목적

딸 폰에서 완료(체크/체크 취소)하거나 보석과 관련해서 자동으로 생기는 기록들(체크 기록, 완료 이력, 보석 장부, 보석 자격)을 서버와 맞춘다. 같은 가족에 속한 아빠 계정은 올리지 않으며, 첫 동기화(P6.13) 이후부터만 올린다.

---

## 쉬운 설명

- **누가**: 딸 폰(자식 역할)
- **무엇을**: 아이가 할 일을 손으로 누르거나 위젯에서 체크/취소한 기록과, 보석 관련 기록(완료 이력, 보석 주는 기준, 보석 자격)
- **언제**: 앱 안에서 변경한 3초 뒤, 또는 앱을 시작/복귀할 때. 위젯에서는 다음 앱을 열 때.
- **어떻게**: 자연 키(natural key) 비교 — 데이터베이스 id가 아니라 실제 내용(할 일 + 날짜, 받은 날짜 등)으로 비교해서 중복 없이 올린다.
- **특별한 점**: 아빠가 서버에서 지운 할 일의 기록은 올리지 않아서 외래키 오류로 동기화가 멈추지 않게 한다.

---

## 필요한 입력

1. **로그인된 딸 계정**: 서버와 가족이 연결된 상태
2. **첫 동기화 기록**: 같은 가족에 대해 P6.13을 이미 한 번 실행했음을 알리는 플래그(`SYNCED_FAMILY_KEY`)
3. **로컬 기록**: 폰의 SQLite 데이터베이스에 있는 `task_completions`, `task_completion_history`, `sticker_ledger`, `gem_rights` 테이블
4. **서버 상태**: 서버의 `tt_task_completions`, `tt_task_completion_history`, `tt_sticker_ledger`, `tt_gem_rights`, `tt_tasks` 테이블

---

## 결과물

1. **올린 기록 개수** (숫자): 추가/수정/삭제한 행의 합계
2. **서버 테이블 변경**:
   - `tt_task_completions`: 체크 기록 추가(체크함)/삭제(체크 취소)

   - `tt_sticker_ledger`: 보석 장부 행 추가/삭제
   - `tt_gem_rights`: 보석 자격 추가/수정(폰 상태가 더 나아가면)

## 수행 순서

### 1단계: 로컬 기록 읽기
```
SELECT * FROM task_completions        → 체크 기록
SELECT * FROM task_completion_history → 완료 이력
SELECT * FROM sticker_ledger WHERE family_id = 'local-family' → 보석 장부
SELECT * FROM gem_rights WHERE family_id = 'local-family'     → 보석 자격
```

### 2단계: 서버 기록과 할 일 목록 읽기
```
서버의 tt_task_completions, tt_task_completion_history, tt_sticker_ledger, tt_gem_rights
서버의 tt_tasks 테이블(지워진 할 일 판단용)
```

### 3단계: 자연 키로 비교해 계획 세우기

**자연 키**:
- **체크 기록**: `(할 일 ID, 완료 날짜)`
- **완료 이력**: `(할 일 ID, 완료 날짜)` (중복 불가, 대신 지우지 않음)
- **보석 장부**: 
  - 하루 완료/보상: `사유` (예: `"daily-completion:2026-10-07"`, `"gem-reward:..."`)
  - 그 밖의 조정: `(사유, 수량, 시각)` (같은 조정이 두 번이면 개수로 센다)
- **보석 자격**: `받은 날짜` (상태는 서버가 더 나아간 것을 따른다)

**비교 규칙**:
- 폰에만 있으면: 올리기
- 서버에만 있으면: 지우기 (단, 완료 이력과 `given` 상태 보석 자격은 지우지 않음)
- 둘 다 있으면: 상태 비교 (보석 자격 상태는 서버가 더 나아가면 서버 것 유지)

### 4단계: 올리기 실행

**순서** (트랜잭션 보호 필요):
1. 체크 기록 삭제(`completionDeletes`)
2. 보석 장부 삭제(`ledgerDeletes`)
3. 보석 자격 삭제(`gemDeletes`)
4. 체크 기록 추가(`completionInserts`) — `upsert` (중복 무시)
5. 완료 이력 추가(`historyInserts`) — `upsert` (중복 무시)
6. 보석 장부 추가(`ledgerInserts`) — `insert`
7. 보석 자격 추가/수정(`gemUpserts`) — `upsert`

### 5단계: 올린 뒤 받아오기

올린 뒤에는 서버 내용이 기준이다. 다만 **올린 뒤 받아오는 사이에 폰에서 새 체크가 생겼으면** 폰 기록을 지키고 다음 동기화에서 다시 올린다(`childChangeVersion()` 비교).

## 언제 올라가는가?

### 앱 안에서의 변경 → 3초 뒤 올라감
- `src/sync/syncSoon.ts` — `requestSyncSoon()`으로 3초 뒤 실행 예약
- 연달아 변경하면 마지막 변경 시점부터 3초 뒤로 밀린다
- 로그인하지 않았거나 등록된 runner가 없으면 예약 안 됨

### 앱 시작/복귀 → 즉시 올라감
- `syncRunner.ts` — `runSync()` 호출 시 자동 포함
- 위젯 체크 대기 항목을 먼저 DB에 반영한 뒤 올린다

### 위젯에서의 체크 → 다음 앱 열 때 올라감
- 위젯의 `WidgetChecksHeadlessService`가 체크를 `widget-touched.json` 대기 파일에 임시 저장
- 앱 시작 시 `applyPendingWidgetChecksNow()`로 DB에 반영
- 그 다음 동기화 흐름에서 올라감

## 실기기에서 발견·수정한 외래키 문제

### 문제
- 서버에서 아빠가 할 일을 삭제한 뒤 아이 폰의 동기화를 실행하면, 폰의 완료 이력이 더 이상 없는 할 일을 가리킨다.
- 올리기 시도 → 외래키 제약 위반 → 서버 쓰기 실패 → 받아오기 실행 안 됨 → 동기화 멈춤

### 수정 (커밋 a5e36fd)
- 올리기 전에 현재 서버에 있는 할 일 ID 목록을 읽어온다 (`ServerChildRecords.taskIds`)
- 올릴 기록 중 서버에 없는 할 일을 가리키는 것은 제외한다:
  - **체크/이력**: 아예 올리지 않음
  - **보석 장부**: 할 일 연결(`task_id`)만 `NULL`로 비우고 올림 (서버의 `ON DELETE SET NULL` 규칙과 같은 결과)
- 이렇게 하면 올리기가 성공하고 받아오기도 실행되어 폰 데이터가 정리된다.

## 참고: 자연 키 비교 상세

이 작업은 데이터베이스의 자동 생성 ID(`id`) 대신 **비즈니스 의미 있는 내용**으로 비교한다:

| 테이블 | 자연 키 | 예시 |
| --- | --- | --- |
| `task_completions` | `(task_id, completion_date)` | 할 일 #2026 을 10월 7일에 완료 |
| `task_completion_history` | `(task_id, completion_date)` | 위와 같음 (완료 이력은 지우지 않음) |
| `sticker_ledger` | 조건부 | 하루 완료: 사유만 / 조정: (사유, 수량, 시각) |
| `gem_rights` | `earned_date` | 10월 5일에 받은 보석 |

이 방식으로 같은 의미의 데이터는 중복되지 않고, 시간대나 기기 차이를 무시한다.
