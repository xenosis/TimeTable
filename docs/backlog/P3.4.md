## 목적

P3.3의 롤링 계산 결과를 Android 앱 소유 예약으로 반영한다. 시간표(timetable) owner와 할 일(tasks) owner는 독립 예약으로 관리되며, 공통 네이티브 교체 경계가 owner별로 기존 세대를 취소하고 최신 세대만 등록·저장·복구하여 중복 예약과 오래된 알림을 막는다.

P3.4의 범위는 다음 두 부분이다:
1. **시간표(timetable) owner의 실제 데이터 흐름**: 시간표를 저장·변경·삭제할 때 관련 예약을 갱신하고, 최종 세대만 남기는 과정.
2. **owner 전체의 공통 교체·부팅 복구 메커니즘**: timetable·tasks 두 owner 모두에 걸쳐, 앱 재시작(DB 재계산)·재부팅(네이티브 pending 복구)·교체 중단 시에도 각 owner별로 이전 세대와 섞이지 않게 최신 세대만 복구하는 자체.

할 일의 조회와 30분 재알림 생성은 P4.8이 담당한다.

## 쉬운 설명

시간표를 바꾸면 예전 알림을 그대로 둔 채 새 알림을 더하지 않는다. 앱이 만든 예약을 먼저 정리한 뒤 지금 저장된 시간표에 맞는 `notify`(화면 알림)와 `alarm`(소리·화면 알람)만 다시 만든다. 휴대폰을 재부팅하거나 앱 프로세스가 다시 시작되어도 아직 오지 않은 최신 예약만 되살린다. 할 일도 같은 방식으로 처리되지만, 할 일 목록 조회와 30분 재알림 규칙은 P4.8이 담당한다.

## 필요한 입력

- P3.3의 7일 롤링 계산 결과: 식별자, 제목, 발화 시각, `notify`/`alarm` 방식
- P3.2의 일반 알림 채널과 알람 채널
- SQLite의 시간표 데이터, 가족 ID, 시간표 모드 및 예외 데이터
- P4.8이 결합해 전달하는 할 일 알림 목록(개별 조회·30분 재알림 계산은 P4.8 범위)
- Android 알림·정확한 알람·필요한 전체화면 알림 권한 상태
- `docs/needs-info-checklist.md`의 P3.4 검증 행렬

관련 구현 위치: `src/notifications/rollingSchedule.ts` (시간표 계산), `src/notifications/taskRollingSchedule.ts` (할 일 조회 및 P4.8 소유 재알림), `src/notifications/RollingRefreshLifecycle.tsx` (앱 수명주기 연결), `src/notifications/rollingOwners.ts` (owner별 독립 재예약), `android/app/src/main/java/com/sewoong/kidtimetable/alarm/RollingAlarmScheduler.kt` (owner별 네이티브 교체).

## 결과물

- 시간표 롤링 결과를 공통 네이티브 교체 경계로 전달하는 실행 경로 (`replaceTimetableRollingNotificationsFromDatabase`)
- 일반 알림은 `RollingNotificationReceiver`, 알람은 `AlarmReceiver`로 등록하는 Android 예약
- `timetable` owner로 구분되는 현재 세대와 교체 중 세대를 저장하고, 실패·중단 시 재등록 가능한 상태로 정리하는 네이티브 스케줄러 (`RollingAlarmScheduler.replace(..., owner="timetable")`)
- 권한이 꺼진 변경·삭제에서도 기존 앱 소유 예약을 제거하는 경로
- 앱 프로세스 재시작·부팅 뒤 미래 예약만 복구하는 `BootReceiver` 경로
- 시간표 데이터의 반복 저장, 제목·시각 변경, 삭제 후 예약 정확성 검증 기록
- timetable·tasks 두 owner의 앱 재시작·재부팅·교체 중단 복구 검증 기록

## 선행 작업

- `P3.3`: 7일 롤링 계산 함수와 단위 테스트 완료.
- `P3.2`: 앱 시작 시 일반·알람 채널 생성 구현과 검토 완료.
- `P4.8`: 할 일 조회 및 30분 재알림 계산을 소유하고, 결과를 P3.4의 네이티브 교체 경계에 함께 전달한다 (`replaceTimetableRollingNotificationsFromDatabase`에서 P4.8 결과를 병합).

## 수행 순서

1. 가족 ID와 시간표 모드에 맞는 데이터를 읽고 P3.3으로 미래 7일 목록을 계산한다.
2. 시간표 목록과 P4.8이 제공한 할 일 목록을 하나의 최신 세대로 결합한다.
3. 각 항목의 ID·제목·발화 시각·알림 방식을 네이티브 교체 경계에 `timetable` owner로 전달한다 (P4.8이 `tasks` owner로 함께 전달).
4. 네이티브 스케줄러가 교체 중 세대를 저장하고, 일반·알람 양쪽 receiver의 이전 앱 소유 예약을 취소한다.
5. 최신 항목을 방식별 receiver와 `AlarmManager`로 등록한 뒤 현재 세대를 저장하고 교체 중 상태를 정리한다.
6. 권한·등록 오류 또는 교체 중단이 발생하면 저장 상태와 활성 예약의 일관성을 확인하고, 재시작·부팅 복구가 미래 항목만 복원하는지 확인한다.
7. `docs/needs-info-checklist.md`의 P3.4 절차대로 딸 폰 실기기에서 시간표 데이터와 공통 메커니즘을 검증한다.
8. 구현·검사·독립 검토 결과의 반영은 메인 실행에서 수행한다. 이 문서 실행에서는 상태 변경을 하지 않는다.

## done_when 확인 방법

`docs/needs-info-checklist.md`의 "P3.4 시간표 예약 · 공통 교체 경계 (딸 폰 실기기)" 섹션에 기록된 대로, 딸 폰(SM-A245N) 실기기에서 다음을 확인한다:

**1~4번: 시간표(timetable) owner의 실제 데이터**
1. 시간표에 현재 시각보다 3분 뒤인 `P3.4 처음` 항목을 저장한다. 같은 내용을 즉시 한 번 더 저장한다.
2. 제목을 `P3.4 마지막`으로 바꾸고 2분 뒤 시각으로 저장한다. 마지막 내용을 다시 한 번 저장한다.
3. `adb shell dumpsys alarm`에서 timetable owner 예약이 마지막 세대 1건만 남는지 확인하거나, 원래 시각과 마지막 시각을 지난 뒤 `P3.4 마지막` 알림만 정확히 한 번 도착하는지 확인한다.
4. 아직 오지 않은 시간표 항목을 만들어 삭제한다. `dumpsys alarm`에서 timetable owner의 활성 예약이 0건인지, 원래 예약 시각에 알림이 오지 않는지 확인한다.

**5~7번: owner 전체의 공통 교체·복구 메커니즘 (두 owner: timetable·tasks)**
5. 미래 시간표 항목과 미완료 할 일(알림 방식 지정)을 하나씩 만든 뒤 앱을 강제 종료하고 다시 연다. 이 경로는 네이티브 pending 세대 복구가 아니라 JS가 시작 시 DB에서 다시 계산해 새 세대로 교체하는 정상 동작이다. `dumpsys alarm`에 두 owner 각각 DB 기준 미래 예약만 남는지 확인한다.
6. 별도의 미래 항목(시간표 1개, 할 일 1개)으로 기기를 재부팅한다. 이 경로는 앱 프로세스 없이 네이티브가 저장해 둔 pending/current 세대를 그대로 복구한다. 부팅 완료 뒤 `dumpsys alarm`에 각 owner의 미래 예약만 다시 등록되는지 확인한다.
7. Debug APK를 사용하여 owner별로 직접 중단을 주입한다(explicit broadcast):
   - `adb shell am broadcast -n com.sewoong.kidtimetable/.alarm.RollingScheduleTestReceiver --es stage after_pending --es owner timetable`
   - `adb shell am broadcast -n com.sewoong.kidtimetable/.alarm.RollingScheduleTestReceiver --es stage after_pending --es owner tasks`
   - `stage`를 `after_first_schedule`로 바꿔 등록 도중 중단도 각 owner에 대해 반복한다.
   - 매 호출 뒤 앱 프로세스를 다시 시작해 두 owner 각각 이전 세대와 섞이지 않은 pending 세대의 미래 예약만 다시 등록되는지 `dumpsys alarm`으로 확인한다.

**8번: 시간표 알람(alarm) 동작**
8. 시간표 알람(alarm 방식)에서는 잠금 화면에서 전체 화면과 반복음이 유지되고, `끄기` 뒤 소리·전체 화면·상단 진행 알림이 사라지는지 확인한다.

**통과 기준**: timetable owner는 실제 시간표 데이터로 재저장·변경·삭제 뒤 예약이 정확히 1건만 남거나 0건이 되고, 딸 폰 잠금 화면 알람이 정상 동작한다. 공통 교체 경계는 두 owner 모두에서 앱 재시작(DB 재계산)·재부팅(네이티브 pending 복구)·교체 중단(네이티브 pending 복구) 뒤 섞이지 않은 최신 세대만 남는다.
