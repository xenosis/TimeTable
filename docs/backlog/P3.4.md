## 목적

P3.3의 롤링 계산 결과를 Android 앱 소유 예약으로 반영한다. 시간표(timetable) owner와 할 일(tasks) owner는 독립 예약으로 관리되며, 공통 네이티브 교체 경계가 owner별로 기존 세대를 취소하고 최신 세대만 등록·저장·복구하여 중복 예약과 오래된 알림을 막는다.

P3.4의 범위는 다음 두 부분이다:
1. **시간표(timetable) owner의 실제 데이터 흐름**: 시간표를 저장·변경·삭제할 때 관련 예약을 갱신하고, 최종 세대만 남기는 과정.
2. **owner 전체의 공통 교체·부팅 복구 메커니즘**: timetable·tasks 두 owner 모두에 걸쳐, 앱 재시작(DB 재계산)·재부팅(네이티브 pending 복구)·교체 중단 시에도 각 owner별로 이전 세대와 섞이지 않게 최신 세대만 복구하는 자체.

할 일의 조회와 30분 재알림 생성은 P4.8이 담당한다.

## 쉬운 설명

시간표를 바꾸면 예전 알림을 그대로 둔 채 새 알림을 더하지 않는다. 앱이 만든 예약을 먼저 정리한 뒤 지금 저장된 시간표에 맞는 `notify`(화면 알림)와 `alarm`(소리·화면 알람)만 다시 만든다. 휴대폰을 재부팅하거나 앱 프로세스가 다시 시작되어도 아직 오지 않은 최신 예약만 되살린다. 할 일도 같은 방식으로 처리되지만, 할 일 목록 조회와 30분 재알림 규칙은 P4.8이 담당한다.

## 결과물

- 시간표 롤링 결과를 공통 네이티브 교체 경계로 전달하는 실행 경로 (`replaceTimetableRollingNotificationsFromDatabase`)
- 일반 알림은 `RollingNotificationReceiver`, 알람은 `AlarmReceiver`로 등록하는 Android 예약
- `timetable` owner로 구분되는 현재 세대와 교체 중 세대를 저장하고, 실패·중단 시 재등록 가능한 상태로 정리하는 네이티브 스케줄러 (`RollingAlarmScheduler.replace(..., owner="timetable")`)
- 권한이 꺼진 변경·삭제에서도 기존 앱 소유 예약을 제거하는 경로
- 부팅 뒤 미래 예약만 복구하는 경로(`WidgetBootReceiver` → `RollingAlarmScheduler.restoreAfterBoot`). 앱 프로세스 재시작은 이 경로가 아니라 JS가 DB로 새 세대를 다시 계산해 교체하는 경로이다
- 시간표 데이터의 반복 저장, 제목·시각 변경, 삭제 후 예약 정확성 검증 기록
- timetable·tasks 두 owner의 앱 재시작·재부팅·교체 중단 복구 검증 기록

## 선행 작업

- `P3.2`: 앱 시작 시 일반·알람 채널 생성 구현과 검토 완료.

## 수행 순서

1. 가족 ID와 시간표 모드에 맞는 데이터를 읽고 P3.3으로 미래 7일 목록을 계산한다.
2. 시간표 목록은 `timetable` owner의 최신 세대로, 할 일 목록(P4.8)은 `tasks` owner의 최신 세대로 각각 독립해서 만든다(`rollingOwners.ts`가 두 owner를 병렬·독립 실행).
3. 각 항목의 ID·제목·발화 시각·알림 방식을 네이티브 교체 경계에 owner별로 전달한다.
4. 네이티브 스케줄러가 교체 중 세대를 저장하고, 일반·알람 양쪽 receiver의 이전 앱 소유 예약을 취소한다.
5. 최신 항목을 방식별 receiver와 `AlarmManager`로 등록한 뒤 현재 세대를 저장하고 교체 중 상태를 정리한다.
6. 권한·등록 오류 또는 교체 중단이 발생하면 저장 상태와 활성 예약의 일관성을 확인하고, 재시작·부팅 복구가 미래 항목만 복원하는지 확인한다.
7. `docs/needs-info-checklist.md`의 P3.4 절차대로 딸 폰 실기기에서 시간표 데이터와 공통 메커니즘을 검증한다.
8. 구현·검사·독립 검토 결과의 반영은 메인 실행에서 수행한다. 이 문서 실행에서는 상태 변경을 하지 않는다.

### 이 검증의 한계 (검토 반영)

- 7번 `after_pending`: 이전 실제 DB 세대(07:00·07:30·08:00)와 섞이지 않았는지는 직접 대조하지 못했다. debug APK로 바꾸면서 앱을 다시 설치해 실제 DB 세대가 없는 상태였고, 확인한 것은 "마지막으로 저장된 pending 세대만 복구된다"까지이다(코드상 `restoreOwnerAfterBoot`는 pending이 있으면 pending만 복구).
- 7번 복구 경로는 앱 프로세스 재시작이 아니라 **재부팅**이다(호출처가 `WidgetBootReceiver` 하나뿐). 체크리스트 문구를 이에 맞게 고쳤다.
- 1~3번: 같은 항목의 제목·시각만 바꾸면 알람 ID(`<항목 id>:<날짜>`)와 URI가 같아 `AlarmManager`가 기존 예약을 자동 교체한다. 항목이 여러 개일 때 하나만 삭제하거나 요일을 바꿔 ID가 달라지는 경로(`replace`의 이전 세대 취소)는 이번에 실기기로 보지 않았다(완료 조건 밖).
- 설계 위험은 별도 작업 `P3.10`으로 분리했다: 부팅 복구가 첫 잠금 해제 뒤에만 일어난다.
- 디버그 전용 `RollingScheduleTestReceiver`의 트리거 오프셋을 +5/+6분에서 +20/+21분으로 바꿨다(재부팅부터 잠금 해제까지 걸리는 시간 동안 항목이 과거가 되면 복구 대상이 0건이 되어 실패와 구분되지 않기 때문). 주입 뒤 20분 안에 재부팅과 첫 잠금 해제를 마쳐야 한다.
