# P2.2 — 로컬 DB: periods / timetable_items / day_exceptions

## 기준 스냅샷

- 백로그 schema version: `1.1`
- 백로그 SHA-256: `215641ca8949fda672c8fc523344f354e1068bd9a53869b2a0299b3df8d172e0`
- 기준 작업 상태: `in_review`
- 이 문서는 기준 스냅샷의 P2.2를 설명한다. 문서 작성과 개발 작업의 완료 상태는 별도로 확인한다.

## 목적

앱의 시간표, 학원·생활 일정, 휴일·예외 날짜를 기기에 저장할 수 있도록 SQLite v1 구조를 마련한다. P2.2의 구현 범위는 `periods`, `timetable_items`, `day_exceptions` 테이블과 DB 초기화·마이그레이션, 일정 저장에 필요한 타입과 저장소다. 여러 시간표를 구분하는 `family_id`를 포함하고, 가족 범위 안에서 교시 번호가 유일하며 일정이 해당 교시를 외래 키로 참조하도록 한다.

## 쉬운 설명

앱을 다시 열어도 시간표가 남아 있도록 기기 안에 세 종류의 표를 만든다. `periods`는 `family_id`별 교시 시간, `timetable_items`는 요일별 일정, `day_exceptions`는 휴일이나 방학처럼 평소 시간표에서 벗어나는 날짜를 담는다. 한 가족 범위에서 같은 교시 번호를 두 번 만들 수 없고, 일정이 교시를 사용할 때는 같은 가족 범위의 교시만 참조한다. 일정은 교시 방식 또는 시작·종료 시각 방식 중 하나만 사용한다. 색과 아이콘은 화면 색상값 자체가 아니라 `color_key`, `icon_key`라는 의미 있는 키로 저장한다.

## 필요한 입력

- 기준 백로그 스냅샷: schema `1.1`, SHA-256 `215641ca8949fda672c8fc523344f354e1068bd9a53869b2a0299b3df8d172e0`
- 선행 작업 P2.1의 시간표 범위 결정: 학교·학원·생활 일정을 모두 포함한다.
- 프로젝트의 SQLite 의존성과 현재 색상·아이콘 키 타입
- P2.2에 정의된 테이블, 마이그레이션, 저장소 및 검증 범위

## 결과물

- `src/db/migrations.ts`: SQLite schema v1과 버전 마이그레이션
- `src/db/database.ts`: `timetable.db` 연결, 외래 키 활성화, Promise 캐시, 마이그레이션 호출
- `src/db/types.ts`: 일정 범주·알림 모드·DB 입력 타입
- `src/db/timetableRepository.ts`: 일정 입력 검증과 `color_key`·`icon_key`를 포함한 저장
- `__tests__/database.test.ts`: schema·마이그레이션·Promise 캐시·저장 검증
- 구현과 검증 결과를 근거로 한 P2.2 완료 기록

현재 구현에서 확인되는 핵심 동작은 다음과 같다.

- DB 연결 Promise를 공유하여 동시에 초기화해도 연결과 마이그레이션이 중복되지 않는다.
- 연결 실패 시 캐시를 비워 다음 시도에서 재초기화할 수 있다.
- SQLite `user_version`을 기준으로 v1 schema를 한 트랜잭션에서 적용하고 실패하면 롤백한다.
- `periods`와 `timetable_items`에 `family_id` 범위를 적용하고, 범위 안의 교시 번호 유일성과 범위가 일치하는 외래 키를 보장한다.
- `timetable_items`는 교시 참조 방식과 시작·종료 시각 방식 중 정확히 하나를 사용하며, `school`·`academy`·`life` 범주를 저장한다.
- `color_key`와 `icon_key`를 일정 데이터에 저장한다.

## 선행 작업

- P2.1: 시간표 범위를 학교·학원·생활 일정으로 확정
- DB에 사용하는 색상·아이콘 키 타입이 프로젝트 테마에 존재해야 한다.
- 기준 요구사항과 백로그의 P2.2 `deps`, `gate`, `done_when`을 같은 스냅샷에서 확인한다.

## 수행 순서

1. 기준 schema version과 SHA-256을 고정하고 P2.2의 의존성과 완료 조건을 확인한다.
2. 테이블 구조와 일정 범주를 기준 요구사항에 맞춰 `periods`, `timetable_items`, `day_exceptions`로 정의한다. `family_id`를 범위 키로 삼아 교시 유일성 및 범위 일치 외래 키를 정한다.
3. DB 연결 Promise 캐시와 SQLite 외래 키 설정을 구현한다.
4. `user_version`을 확인해 schema v1을 트랜잭션으로 적용하고 실패 시 롤백한다.
5. 일정 타입과 저장소를 구현해 교시 방식과 시각 범위 방식이 섞이지 않도록 검증하고, 색·아이콘의 의미 키가 함께 저장되도록 한다.
6. `__tests__/database.test.ts`로 schema, 마이그레이션, 동시 초기화, 저장 입력을 검증한다.
7. 프로젝트 품질 검사를 실행하고 결과를 기록한다. family 범위 제약과 교시·시각 범위 단일 방식 제약을 반영한 뒤 재검증이 통과하는지 확인한다.
8. 기준 SHA-256을 유지한 채 `critical-reviewer`와 `backlog-explainer`의 검토 결과를 확인한다. 지적이 있으면 구현과 검증을 보완한 뒤 다시 확인한다.
9. `done_when`, 의존성, 검증, 리뷰 결과가 모두 충족될 때만 개발 상태를 `done`으로 기록한다.

## done_when 확인 방법

P2.2의 기준 백로그 항목에 적힌 완료 조건을 다음 근거와 대조한다.

- 세 테이블이 schema v1 마이그레이션에 포함되고 정상 생성되는지 확인한다.
- `family_id`가 교시와 일정의 범위를 나타내고, `periods`의 `(family_id, period_no)`가 범위 안에서 유일하며 일정의 외래 키가 같은 family 범위를 강제하는지 확인한다.
- 일정이 교시 참조 방식 또는 시작·종료 시각 방식 중 하나만 사용하도록 schema와 저장소가 함께 제약하는지 확인한다.
- DB Promise 캐시가 동시 호출에서 공유되고 초기화 실패 뒤 재시도 가능한지 `__tests__/database.test.ts`에서 확인한다.
- 일정 저장소가 학교·학원·생활 일정과 필수 입력을 검증하며 `color_key`, `icon_key`를 저장하는지 확인한다.
- `npm run check`의 지침 동기화, 코드 길이, lint, typecheck, 테스트, Android debug build 결과를 확인한다.
- family 범위, 교시 유일성·외래 키, 교시·시각 범위 단일 방식 제약을 반영한 재검증이 통과했는지 확인한다.
- 등록된 `critical-reviewer`와 `backlog-explainer`가 동일한 기준 SHA-256을 검토했는지 확인한다.
- P2.1 의존성과 P2.2의 모든 하위 조건이 충족되었는지 확인한 뒤에만 `in_review`에서 `done`으로 변경한다.
