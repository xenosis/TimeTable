### P2 시간표 로컬 통합 확인

현재 홈·관리자 화면 분리 구조에서 아래 순서로 확인한다.

1. 홈의 `관리자 설정`을 누른다. PIN을 입력하기 전에는 교시·시간표 편집 화면이 보이지 않아야 한다.

3. 시간표 항목을 추가하고 수정한 뒤 홈으로 돌아간다. 오늘 시간표와 주간 시간표에 바뀐 제목·시각이 바로 반영되는지 확인한다.
4. 요일 복사로 원본 요일을 다른 요일에 복사한다. 대상 요일의 주간 시간표가 원본과 같아지는지 확인한다.
5. 앱을 완전히 종료한 뒤 다시 연다. 교시와 시간표 변경 내용이 그대로 남아 있는지 확인한다.

통과 기준: PIN 보호 뒤 저장한 시간표가 홈의 오늘·주간 화면에 반영되고, 요일 복사와 앱 재시작 뒤에도 로컬 데이터가 유지된다.

### P3.4 시간표 예약 · 공통 교체 경계 (딸 폰 실기기)

P3.1·P3.2는 완료됐다. **모든 단계를 딸 폰(SM-A245N) 실기기에서 진행한다.** 1~6·8번은 서버가 필요 없는 **`TimeTable-v*-OfflineTest-Device-arm64-v8a.apk`**(release)로 진행한다. **7번(교체 중단 주입)만은 debug APK**를 딸 폰에 설치하고 PC와 같은 Wi-Fi에서 개발 서버에 연결한 상태로 진행한다 — 중단 주입용 `RollingScheduleTestReceiver`는 debug 빌드에만 포함되어 release(OfflineTest) APK에는 없다. 두 APK는 서명이 달라 전환할 때 기존 앱을 삭제해야 한다.

P3.4는 **시간표(timetable) owner의 실제 데이터 흐름**과 **owner에 상관없이 공통으로 쓰는 교체·복구 메커니즘 자체**를 확인한다. 실제 할 일(tasks) 데이터로 하는 검증은 P4.8 절로 옮겼다. 메커니즘 확인(5~7번)은 timetable·tasks 두 owner 모두 합성 데이터로 함께 확인한다(둘 다 같은 코드 경로를 타므로).

1. **[시간표 데이터]** 시간표에 현재 시각보다 3분 뒤인 `P3.4 처음` 항목을 저장한다. 같은 내용을 즉시 한 번 더 저장한다.
2. **[시간표 데이터]** 제목을 `P3.4 마지막`으로 바꾸고 2분 뒤 시각으로 저장한다. 마지막 내용을 다시 한 번 저장한다.
3. **[시간표 데이터]** `adb shell dumpsys alarm`에서 timetable owner 예약이 마지막 세대 1건만 남는지 확인하거나, 원래 시각과 마지막 시각을 지난 뒤 `P3.4 마지막` 알림만 정확히 한 번 도착하는지 확인한다.
4. **[시간표 데이터]** 아직 오지 않은 시간표 항목을 만들어 삭제한다. `dumpsys alarm`에서 timetable owner의 활성 예약이 0건인지, 원래 예약 시각에 알림이 오지 않는지 확인한다.
5. **[공통 메커니즘, 두 owner]** 미래 시간표 항목과 미완료 할 일(알림 방식 지정)을 하나씩 만든 뒤 앱을 강제 종료하고 다시 연다. **이 경로는 네이티브 pending 세대 복구가 아니라 JS가 시작 시 DB에서 다시 계산해 새 세대로 교체하는 것이다(정상 동작).** `dumpsys alarm`에 두 owner 각각 DB 기준 미래 예약만 남는지 확인한다.
6. **[공통 메커니즘, 두 owner]** 별도의 미래 항목(시간표 1개, 할 일 1개)으로 기기를 재부팅한다. **이 경로는 앱 프로세스 없이 네이티브가 저장해 둔 pending/current 세대를 그대로 복구하는 것이다.** 부팅 완료 뒤 `dumpsys alarm`에 각 owner의 미래 예약만 다시 등록되는지 확인한다.
7. **[공통 메커니즘, 두 owner, debug APK]** 아래처럼 owner별로 직접 중단을 주입한다(explicit broadcast):
   - `adb shell am broadcast -n com.chaea.timetable/.alarm.RollingScheduleTestReceiver --es stage after_pending --es owner timetable`
   - `adb shell am broadcast -n com.chaea.timetable/.alarm.RollingScheduleTestReceiver --es stage after_pending --es owner tasks`
   - `stage`를 `after_first_schedule`로 바꿔 등록 도중 중단도 각 owner에 대해 반복한다.
   - 주입한 테스트 알람은 주입 시각 +20분(첫 예약, 알림)과 +21분(두 번째, 알람)이다. **주입 뒤 20분 안에 기기를 재부팅하고 첫 잠금 해제까지 마친다.**
   - 복구는 앱 프로세스 재시작이 아니라 **재부팅(`WidgetBootReceiver`)** 으로만 일어난다(앱을 다시 열면 JS가 DB로 새 세대를 계산해 pending을 덮어쓰므로 pending 복구를 볼 수 없다). 앱을 열지 않은 채 `dumpsys alarm`으로 두 owner 각각 마지막 pending 세대의 미래 예약만 다시 등록됐는지 확인한다. `after_first_schedule`는 중단 직후 대기 알람이 0건이고(첫 예약은 catch가 취소), 재부팅 뒤 첫·두 번째 예약이 모두 복구되어야 한다.
8. **[시간표 데이터]** 시간표 알람(alarm 방식)에서는 잠금 화면에서 전체 화면과 반복음이 유지되고, `끄기` 뒤 소리·전체 화면·상단 진행 알림이 사라지는지 확인한다.

통과 기준: timetable owner는 실제 시간표 데이터로 재저장·변경·삭제 뒤 예약이 정확히 1건만 남거나 0건이 되고, 딸 폰 잠금 화면 알람이 정상 동작한다. 공통 교체 경계는 두 owner 모두에서 앱 재시작(DB 재계산)·재부팅(네이티브 pending 복구)·교체 중단(네이티브 pending 복구) 뒤 섞이지 않은 최신 세대만 남는다.

### P4.8 할 일(tasks) owner 실제 예약 확인 (딸 폰 실기기)

P3.4의 공통 교체 경계 확인(5~7번)이 먼저 끝나 있어야 한다. **`TimeTable-v*-OfflineTest-Device-arm64-v8a.apk`**로 딸 폰에서 진행한다. 할 일(tasks) owner는 미완료 상태면 첫 알림 외에 30분 뒤 재알림이 하나 더 정상 생성되므로 기대 건수가 시간표와 다르다: **완료 전 2건(첫 알림 + 30분 재알림), 완료 체크 뒤 0건.**

1. 알림 방식을 지정한 미완료 할 일을 현재 시각보다 3분 뒤로 저장한다. 같은 내용을 즉시 한 번 더 저장한다.
2. 제목을 바꾸고 2분 뒤 시각으로 저장한다. 마지막 내용을 다시 한 번 저장한다.
3. `dumpsys alarm`에서 tasks owner 예약이 마지막 세대(첫 알림 + 30분 재알림 2건)만 남는지 확인하거나, 실제로 두 알림이 순서대로 도착하는지 확인한다.
4. 같은 할 일을 완료 체크한다. `dumpsys alarm`에서 tasks owner의 해당 할 일 재알림이 취소돼 0건인지 확인한다.
5. 알람 방식으로 설정한 할 일로 위 P3.4의 8번과 같은 잠금 화면 알람(전체 화면·반복음·끄기)을 확인한다.
6. 아직 오지 않은 할 일을 삭제한다. `dumpsys alarm`에서 tasks owner의 활성 예약이 0건인지 확인한다.

통과 기준: tasks owner는 실제 할 일 데이터로 재저장·제목/시각 변경·완료 체크·삭제 각각에서 기대 건수(완료 전 2건, 완료·삭제 후 0건)만 정확히 남고, 딸 폰 잠금 화면 알람이 정상 동작한다.

### P4.7 보석판 · P4.13 연속 자격 (최신 정책)

P4.6 자동 적립은 cancelled다. 최신 정책은 `docs/backlog/P4.13.md`의 확정 정책과 그 이후 변경을 따른다. **앱은 보석 장부를 자동으로 늘리거나 줄이지 않으며 딸의 직접 입력만 개수를 바꾼다.** 할 일이 있는 날의 전체 완료가 5일 연속이면 실물 보석을 받을 자격이 생기고, 할 일이 없는 날은 건너뛴다. 새 할 일은 생성한 날부터만 판정한다.

1. 오늘의 새 할 일을 두 개 이상 준비한다.
2. 하나만 완료한다. 진행률만 바뀌고 보석 수가 늘지 않는지 확인한다.
3. 나머지도 완료한다. `오늘 할 일을 모두 해냈어요!` 문구가 커져서 보이고 `N일 연속 완료`가 바로 갱신되는지 확인한다.
4. 마지막 완료를 취소한다. 축하 문구와 연속 일수가 되돌아가는지 확인한다.
5. 앱을 완전히 닫았다가 열어 실제 완료 상태와 보석판이 유지되는지 확인한다.
6. 작은/큰 보석 개수를 직접 수정하고 재시작 후 유지되는지 확인한다. 확인 후 원래 수량으로 복원한다.
7. 관리자에서 보상 목표 이름과 필요 보석 수를 저장한다. 보석판에 남은 개수가 맞게 보이고 목표 달성 처리 후에도 장부 수량이 유지되는지 확인한다.
8. 받을 자격이 있으면 딸의 전체 요청, 아빠의 지급 처리, 요청/지급 후 장부 불변을 확인한다. 요청 전 체크 취소 시 자격 회수, 요청·지급 후에는 자격 기록 유지도 확인한다.

테마 그림의 큰 보석=작은 보석 5점 계산은 시각 표현만 바꾼다. 자격·목표·장부 정책의 환산이나 자동 적립 검증으로 쓰지 않는다. 실제 자격 흐름을 확인하지 못한 경우 SQLite/렌더 테스트와 구분해 미확인으로 남긴다.

4. 방학 모드에서 요일 복사를 해 보고 평소 시간표에는 영향이 없는지 확인한다.
5. 앱을 닫았다 다시 열어 마지막 모드가 유지되는지 확인한다.

통과 기준: 평소와 방학 시간표가 분리되고, 선택한 모드가 화면 전체와 재실행 뒤에도 적용된다.

## 제공해야 하는 정보

### P8.1 NEIS 시간표 · P8.2 급식

두 기능에는 같은 정보가 필요하다.

- 교육정보 개방 포털에서 발급한 NEIS 인증키
- 교육청 코드와 학교 코드
- 조회할 학년도와 학기

인증키는 채팅에 그대로 올리지 말고, 안전하게 전달할 방법을 정한 뒤 입력한다. 정보를 받으면 해당 학교에 실제 데이터가 있는지 확인하고 시간표와 급식 화면을 구현·검증한다.

## 나중에 처리할 항목

### P1.7 서명 키 백업 · P1.8 첫 릴리즈 설치

첫 실기기용 릴리즈 APK 설치·실행은 이미 확인됐다. 사용자가 결정한 대로 서명 키와 비밀번호 파일의 외부 안전 보관은 **첫 장기 사용 또는 실제 배포 직전**에 진행한다. 그때 두 파일을 함께 안전한 프로젝트 밖 위치에 보관한 사실만 알려 주면 된다. 비밀번호는 채팅에 적지 않는다.

### P8.4 아빠용 주간 리포트

아빠 폰과 딸 폰의 데이터를 함께 보여 주려면 P6 동기화와 아빠용 화면이 먼저 필요하다. 동기화 작업이 끝난 뒤 서버 데이터를 기준으로 구현한다.
