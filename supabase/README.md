# TimeTable 서버(Supabase) 스키마

앱 로컬 SQLite(`src/db/migrations.ts`, 버전 11)와 같은 모양의 서버 테이블입니다. 백로그 P6.2(스키마)와 P6.3(보안 규칙)에서 만들었습니다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `migrations/20261001000000_tt_schema.sql` | 테이블 13개, 제약, 인덱스, `updated_at` 트리거 |
| `migrations/20261001000100_tt_rls.sql` | 소속 확인 함수, 가족 만들기 함수, 행 수준 보안(RLS) 정책 |

- 모든 테이블 이름에 `tt_` 접두사를 붙였습니다. Doro와 같은 프로젝트에 넣어도 이름이 겹치지 않고, 새 프로젝트에 넣어도 그대로 쓸 수 있습니다.
- Postgres 15 이상이 필요합니다(`on delete set null (열)` 문법). Supabase 신규 프로젝트는 기본으로 만족합니다.
- **적용 대상(2026-10-05 결정): Doro와 같은 Supabase 프로젝트.** 계정은 아빠·딸 기기용 이메일+비밀번호 2개를 대시보드 Authentication에서 만들고, 적용은 `npx supabase` CLI로 합니다.
- **테이블 권한**: Supabase는 2026-10-30부터 기존 프로젝트에서도 public의 새 테이블을 Data API에 자동 노출하지 않습니다(changelog 45329). 그래서 RLS 파일에서 tt_ 테이블과 id 시퀀스에만 authenticated·service_role 권한을 직접 주고 anon 권한은 회수합니다. Doro 테이블에 영향을 주는 스키마 전체 grant는 쓰지 않습니다.
- **적용 완료(2026-10-05)**: Doro 프로젝트(PostgreSQL 17)에 두 파일을 한 트랜잭션(BEGIN…COMMIT)으로 `npx supabase db query --linked -f`로 실행했습니다. Doro 프로젝트에 마이그레이션 이력 테이블이 없어(대시보드로 관리) 이력은 남기지 않았습니다. 적용 전 tt_ 테이블·tt_private 스키마가 없음을, 적용 뒤 Doro 테이블 3개가 그대로임을 확인했습니다.
- **적용 결과 확인**: tt_ 테이블 13개 모두 RLS 켜짐, 정책은 테이블당 1~4개, anon은 모든 테이블 읽기·쓰기 권한 없음, authenticated는 읽기·쓰기 권한(행 범위는 RLS). 보안 함수 3개는 anon이 실행할 수 없습니다.
- **보석 자격·이전 함수 적용(2026-10-06, P6.5)**: `20261006000000_tt_gem_rights_import.sql`(tt_gem_rights 테이블·RLS·권한, `tt_import_local` 함수)을 같은 방식(BEGIN…COMMIT, `db query -f`)으로 적용했다. 적용 전 같은 트랜잭션 안에서 마이그레이션과 `tests/tt_import_check.sql`을 함께 실행해 15건 통과를 확인하고 되돌렸고, 적용 뒤 다시 15건 통과·`tt_rls_check.sql` 59건 통과·advisors 새 경고 없음을 확인했다. 이전 함수는 security invoker(RLS 적용)라 가족 구성원만 자기 가족에 넣을 수 있고, 서버가 새 id를 붙여 로컬 id→서버 id를 함수 안에서 짝지으며, 가족에 데이터가 이미 있으면 아무것도 넣지 않고 멈춘다.
- **관리자 편집 저장 함수 적용(2026-10-07, P6.15 리뷰 반영)**: `20261007000000_tt_apply_family_edit.sql`(`tt_apply_family_edit`)을 같은 방식으로 적용했다. 로그인한 폰의 편집 전후 비교 결과를 한 트랜잭션으로 저장하고(일부만 남지 않음), 새 행은 폰이 정한 id로 넣되 같은 id가 있으면 덮어쓰지 않고 거부하며, 서버에 없는 행 고치기(되살리기)와 완료 이력이 있는 할 일 지우기를 거부한다. security invoker(RLS 적용), 같은 가족 동시 호출은 트랜잭션 잠금. 적용 전 같은 트랜잭션 안에서 `tests/tt_family_edit_check.sql` 10건 통과를 확인하고 되돌렸고, 적용 뒤 편집 10건·이전 17건·RLS 59건 통과, advisors 새 경고 없음. 주의: 가족 데이터 테이블(교시·세트·항목·휴일·할 일·보상)의 새 행 id는 앱이 정하므로 SQL로 직접 넣을 때는 id 시퀀스(기본값)와 겹칠 수 있다. 시험 데이터를 넣을 때는 id를 큰 수로 직접 정한다.
- **보안 규칙 실행 검증**: `tests/tt_rls_check.sql`(가짜 사용자로 한 트랜잭션 안에서 검사하고 모두 되돌림) **59건 통과(허용 33·거부 26, 2026-10-05)** — 아빠 A·딸 A·다른 가족 아빠 B·가족 없는 사용자·anon. 다른 가족으로 행 옮기기(WITH CHECK), 남의 기기 쓰기, 딸의 아빠 강등·삭제, 가족 직접 추가·삭제, 완료 이력·시간표 설정, 삭제 정책, 아빠의 관리 권한(딸 기기 읽기·삭제, 구성원 수정·추가·삭제, 가족 삭제), 딸의 자기 기기 등록·완료 취소·시간표 세트/항목 쓰기를 포함합니다. 마지막에 소유자 권한으로 0행 거부 대상 데이터가 그대로인지 확인합니다. '거부'는 권한·RLS 거부(42501), 정책 조건에 따른 0행, 그리고 검사마다 명시한 의도된 오류(코드와 메시지가 모두 맞을 때만. 예: tt_create_family의 'already in a family')만 인정하고, 중복·외래키 같은 다른 오류는 `error:<코드>`로 따로 기록합니다(처음 28건 버전은 중복 제약 실패도 거부로 셌던 문제를 리뷰에서 지적받아 고침). 결과 원본: `.tmp/tt-rls-check-result-2026-10-05.json`. 실행 뒤 tt_ 데이터와 검증용 사용자가 남지 않았음을 확인했습니다. 가짜 사용자를 운영 DB의 `auth.users`에 넣으므로 실행 전 그 테이블에 트리거가 없는지 확인합니다(2026-10-05: 없음). 실행: `npx supabase db query --linked --project-ref <ref> -f supabase/tests/tt_rls_check.sql` (결과는 오류 메시지의 TT_RLS_RESULT JSON).
- **`tt_create_family` 동시 호출**: 같은 사용자가 동시에 두 번 불러 둘 다 '이미 소속' 검사를 통과해도, 두 번째 구성원 추가가 `unique (user_id)`에 걸려 그 호출 전체가 되돌려지므로 빈 가족이 남지 않습니다.
- **받아들인 위험(2026-10-05 사용자 판단)**: (1) Doro의 `schedules` 정책은 로그인한 사용자 누구나 전체 읽기·쓰기(`using true`)라, 같은 프로젝트에 만든 딸 계정의 로그인 정보가 유출되면 Doro 일정에도 접근할 수 있습니다. 앱은 Doro 테이블을 쓰지 않고, 이 프로젝트는 공개 가입 없이 사용자를 직접 추가하므로 외부인은 계정을 만들 수 없어 그대로 둡니다. (2) 텍스트 열 길이 제한이 없고, 아빠는 임의의 사용자 id를 자기 가족 구성원으로 넣을 수 있습니다(가족 앱 운영에서 문제 삼지 않음). (3) 같은 가족 안에서는 보석 원장 `child_id`를 아빠로 적어도 막지 않습니다(앱이 딸 id만 씀). (4) 서버 규칙상 아빠는 자기 역할을 child로 바꾸거나 자기 구성원 행을 지울 수 있어, 그러면 관리할 parent가 없는 가족이 남을 수 있습니다. 앱에 그런 기능을 넣지 않으므로 고려하지 않습니다(2026-10-06 사용자 판단).
- **보안 점검(`supabase db advisors`)**: tt_ 관련 경고 1건 — `tt_create_family`가 SECURITY DEFINER인데 authenticated가 RPC로 호출할 수 있음. 가족과 첫 parent 구성원을 함께 만들려면 RLS를 우회해야 하므로 의도한 설계로 유지합니다(함수 안에서 로그인 여부와 기존 소속을 확인, anon 실행 권한 회수, 검증에서 딸·anon의 호출 거부 확인). 나머지는 데이터가 없어 생긴 '사용되지 않은 인덱스' 안내(INFO)입니다.
- `__tests__/supabase-migrations.test.ts`는 파일 내용을 정적으로 검사합니다(실행 검증은 위 tests 파일).

## 적용 순서

1. (2026-10-05 적용 완료, 커밋 5caf233의 두 파일) 두 파일을 순서대로 한 트랜잭션(BEGIN…COMMIT)으로 묶어 `npx supabase db query --linked --project-ref <ref> -f <파일>`로 실행합니다. **`supabase db push`는 쓰지 않습니다**: Doro 공유 프로젝트에는 마이그레이션 이력 테이블이 없어, push하면 이력 스키마가 새로 생기고 이미 만든 테이블을 다시 만들려다 실패합니다. 이후 변경(P6.7 Realtime 게시 등)도 새 SQL 파일을 같은 방식으로 실행하고, 적용 날짜·커밋을 이 README에 적습니다. 이력 테이블을 둘지(`migration repair`)는 Doro 프로젝트를 건드리는 일이라 사용자 확인 뒤에 정합니다.
2. 아빠 계정으로 로그인한 상태에서 가족을 만듭니다: `select public.tt_create_family('우리 가족', '아빠');` (가족과 첫 구성원 parent가 함께 만들어집니다.)
3. 딸 기기용 계정(Authentication 메뉴에서 사용자 추가)을 만든 뒤, 아빠 계정으로 구성원에 넣습니다:
   `insert into public.tt_family_members (family_id, user_id, role, display_name) values ('<가족 id>', '<딸 계정 user id>', 'child', '딸');`

## 권한 요약 (D7: 딸 폰 PIN은 로컬 화면 잠금)

| 데이터 | 아빠 (parent) | 딸 기기 (child) |
| --- | --- | --- |
| 시간표·교시·시간표 세트·휴일, 할 일, 완료 기록, 보석 원장, 보상 목표 | 읽기·쓰기 | 읽기·쓰기 |
| 가족 정보 수정, 구성원 추가·삭제 | 가능 | 불가(읽기만) |
| 기기 정보(푸시 토큰, 마지막 동기화) | 가족 기기 읽기·삭제, 자기 것 쓰기 | 자기 것 읽기·쓰기 |
| 로그인하지 않은 사용자 | 접근 불가 | 접근 불가 |

딸 폰에서 PIN을 통과하면 시간표와 할 일을 고칠 수 있어야 하고, 완료 체크와 보석 적립은 앱이 직접 기록하므로 딸 계정에도 쓰기 권한이 있습니다. 대신 딸 기기의 로그인 정보만 있으면 서버 데이터를 고칠 수 있습니다(받아들인 설계).

| 가족 id | `'local-family'` 문자열 | uuid (`tt_families.id`) |

## 로컬 데이터 최초 이전 (P6.5, 2026-10-06)

로컬 id를 그대로 넣지 않습니다. `tt_import_local`이 서버 id를 새로 붙이고, 함수 안에서 로컬 id → 서버 id를 짝지어 세트·할 일 참조를 유지합니다(앱 계정에는 시퀀스를 맞출 권한이 없음). 보완(`20261006000100_tt_import_guard.sql`): 이 가족의 딸 계정으로 로그인한 사람만 부를 수 있고 원장·보석 자격의 주인은 호출한 딸이며, 같은 가족에 대한 동시 호출은 트랜잭션 잠금으로 하나씩 처리합니다. 2026-10-06 딸 폰에서 한 번 실행했고(시험용 데이터였음), 사용자 요청으로 같은 날 서버의 이전 데이터(시간표 항목·할 일·완료 이력)를 지웠습니다(가족·구성원·시간표 세트는 남김).

## 동기화(P6.5·P6.6) 설계 때 주의할 점

- **삭제는 전파되지 않습니다.** 완료 취소와 원장 정정은 행을 지우는데 삭제 기록(tombstone)이 없고, `updated_at`은 서버가 바꾼 시각이라 "나중에 올린 쪽이 이깁니다". 증분 동기화가 아니라 전체 스냅샷 비교로 할지, 삭제 기록을 둘지는 P6.6에서 정합니다.
- **`tt_sticker_ledger`의 부분 unique 인덱스**(`daily-completion:%`, `gem-reward:%`)는 supabase-js `upsert(onConflict)`의 충돌 대상으로 쓸 수 없습니다. 올릴 때는 일반 insert 후 중복 오류(23505)를 무시하는 방식을 씁니다.
- **id 발급**: 서버 id는 서버가 붙입니다(P6.5 이전 함수도 같음). 로컬 id와 서버 id는 다르므로, 로컬 행과 서버 행을 맞추는 방법(서버 기준으로 내려받아 바꾸기 등)은 P6.6에서 정합니다.
- **이전 전처리(P6.5 구현)**: `set_id`가 없는 시간표 항목이나 할 일이 없는 완료 기록이 있으면 이전 전체를 거부하고 되돌립니다. 잘못된 날짜·시각은 서버 제약이 거부합니다. `task_completions`는 앱이 할 일을 거쳐 이 가족 것만 모으고, 원장·보석 자격의 `'local-child'`는 호출한 딸 계정으로 바꿉니다.
- **구성원 관리**: 마지막 아빠(parent)를 삭제하거나 child로 바꾸면 관리자가 없는 가족이 되어 복구할 수 없습니다. 운영할 때 하지 않습니다(DB에서 막지는 않았습니다).
- **보석 원장이 있는 구성원은 지울 수 없습니다.** 계정을 다시 만들어야 하면 원장의 `child_id`를 새 계정으로 옮긴 뒤 지웁니다.

## 일부러 하지 않은 것

- **서버 PIN 확인 함수, `parent_pin_hash`**: D7 결정으로 만들지 않았습니다.
- **`force row level security`**: 소유자 권한으로 도는 확인 함수가 정책에 막힐 수 있어 쓰지 않았습니다.
- **"오늘 것만 체크/취소" 제한**: 오프라인에서 체크한 기록이 나중에 올라오므로 날짜 제한을 두지 않았습니다.
- **Realtime 게시(publication) 등록(2026-10-07 적용, P6.7)**: `20261007000100_tt_realtime.sql`로 가족 데이터 테이블 11개(교시·세트·적용 세트·항목·휴일·할 일·체크·완료 이력·장부·보상·보석 자격)를 `supabase_realtime`에 넣고 `replica identity full`을 켰다(삭제 이벤트에는 RLS가 적용되지 않으므로, 이전 행 전체를 실어 family_id 필터로 이 가족 것만 받기 위해). `tt_devices`(동기화마다 갱신)·`tt_families`·`tt_family_members`는 넣지 않았다. 적용 전 게시는 비어 있었다(Doro는 쓰지 않음).
